# 08 工程架构设计

本文档定义 Web 文明类游戏第一版原型的工程边界。目标不是先做一个“完整大引擎”，而是建立一套可测试、可存档、可回放、可逐步扩展的架构，让 30 回合核心循环能稳定跑通。

默认技术路线：

| 项目 | 决策 |
| --- | --- |
| 平台 | 桌面浏览器 Web Demo 优先 |
| 技术栈 | TypeScript + Vite + PixiJS/WebGL + React DOM UI |
| 渲染边界 | PixiJS 负责地图、单位、资源、战争迷雾、选中高亮、路径预览 |
| UI 边界 | React/DOM 负责城市面板、科技树、外交面板、Tooltip、日志、调试工具 |
| 规则边界 | Simulation 负责所有规则结算，渲染层和 UI 不直接改 GameState |
| 后台计算 | AI、寻路、地图生成、胜利评估预留 Web Worker |
| 存档 | IndexedDB 保存 GameState 快照，LocalStorage 只保存设置 |

## 一、架构总览表

| 层级 | 核心对象 | 主要职责 | 不负责 |
| --- | --- | --- | --- |
| State | `GameState` | 保存地图、玩家、城市、单位、科技、外交、胜利进度、回合数、随机种子。 | 不做渲染，不直接处理 DOM 事件。 |
| Input | `InputController` | 把鼠标、键盘、滚轮、Pointer Events 转成用户意图。 | 不直接修改单位位置或资源。 |
| Command | `RuleCommand` | 表达会改变规则状态的动作，例如移动、建造、研究、攻击、结束回合。 | 不承载选中、hover、相机、面板展开等 UI 状态。 |
| Validation | `Validator` | 判断 Command 是否合法，并给出失败原因。 | 不产生副作用。 |
| Simulation | `Simulation` | 执行合法 Command，处理回合结算、资源增长、生产、科技、战斗、胜利检测。 | 不持有 PixiJS 对象，不依赖 React 组件。 |
| Event | `EventLog` | 记录规则变化、玩家操作、AI 意图、资源结算、错误原因。 | 不作为唯一状态源。 |
| Render | `RenderEngine` | 根据 GameState 和 UI 选择态绘制地图、单位、资源、战争迷雾、高亮。 | 不决定规则结果。 |
| UI | `React UI` | 展示面板、按钮、Tooltip、百科、日志、调试信息，并提交 Command。 | 不在组件内部私自改规则数据。 |
| Worker | `WorkerHost` / `WorkerClient` | 后台执行 AI、寻路、地图生成、胜利评估等耗时任务。 | 不持有不可序列化对象，不直接访问 DOM。 |
| Storage | `StorageService` | 保存、读取、迁移 GameState 存档和轻量设置。 | 不改变游戏规则。 |
| Assets | `AssetManager` | 加载地形图集、单位图集、图标、音频、配置表。 | 不保存规则状态。 |

## 二、模块职责表

| 模块 | 输入 | 输出 | 第一版要求 |
| --- | --- | --- | --- |
| `GameState` | 初始配置、地图种子、Simulation 结果 | 可序列化状态树 | 必须纯数据化，能 JSON 化或结构化克隆。 |
| `CommandBus` | UI/Input/AI/System Command | 验证结果、状态变更、事件日志 | 所有规则动作都走 Command。 |
| `Validator` | `GameState` + `Command` | `ValidationResult` | 必须返回明确失败原因，供 Tooltip/日志展示。 |
| `Simulation` | 当前 `GameState` + 合法 `Command` | 新 `GameState` + `GameEvent[]` | 使用不可变或可控 mutation，保证调试可追踪。 |
| `TurnSystem` | 回合结束 Command、AI Command | 回合结算事件、新回合状态 | 结算顺序固定并写入日志。 |
| `RenderEngine` | `GameState`、Camera、Selection、Overlay | PixiJS 舞台画面 | 只读状态，使用 diff 更新 Sprite。 |
| `React UI` | `GameState` 派生选择器、EventLog | DOM 面板、按钮、Command | UI 状态和规则状态分离。 |
| `WorkerClient` | 可序列化请求 | 可序列化响应 | 支持 requestId、超时、取消、错误返回。 |
| `StorageService` | SaveGame、Settings | IndexedDB 存档、LocalStorage 设置 | 存档带 `schemaVersion` 和 `buildVersion`。 |
| `DebugTools` | GameState、EventLog、性能指标 | 调试面板、导出 JSON | 第一版必须有 FPS、回合日志、AI 意图、坐标层。 |

## 三、数据流

### 1. 玩家操作数据流

```text
Pointer/Keyboard
  -> InputController
  -> CommandFactory
  -> CommandBus
  -> Validator
  -> Simulation
  -> GameStateStore
  -> React UI selectors
  -> RenderEngine sync
  -> EventLog / DebugTools
```

说明：

| 环节 | 设计要求 |
| --- | --- |
| 输入层 | 只识别“玩家想做什么”，例如选中单位、移动到地块、打开城市面板。 |
| UIIntent 层 | 选中、hover、打开面板、相机变化只更新 `UIState`，不进入规则回放。 |
| Command 层 | 只有会改变规则结果的意图才变成结构化 `RuleCommand`，带 `actorId`、`turn`、`payload`。 |
| Validator | 先判定是否合法，例如移动力不足、地块不可达、科技前置不满足。 |
| Simulation | 只有合法 Command 才能改变 GameState。 |
| UI/Render | 状态改变后统一刷新，不各自保存一份规则数据。 |

### 2. AI 操作数据流

```text
GameState snapshot
  -> WorkerClient.request("AI_PLAN")
  -> AI Worker
  -> Candidate Command[]
  -> Validator
  -> Simulation
  -> GameStateStore
  -> EventLog
```

说明：

| 环节 | 设计要求 |
| --- | --- |
| AI 输入 | 使用裁剪后的 `AIReadableState`，避免把全部 UI 状态传给 Worker。 |
| AI 输出 | 输出 Command 列表，而不是直接输出新 GameState。 |
| 主线程验证 | AI 生成的 Command 仍然必须经过 Validator。 |
| 可解释性 | AI 每个关键 Command 需要带 `reason`，用于调试面板展示。 |

### 3. 存档数据流

```text
GameState + EventLog summary + Metadata
  -> SaveGame
  -> StorageService
  -> IndexedDB
```

读档：

```text
IndexedDB
  -> StorageService
  -> migrateSaveGame(schemaVersion)
  -> GameStateStore
  -> React UI / RenderEngine
```

第一版存档保存当前局快照，回放使用 CommandLog 预留结构。不要把 PixiJS Sprite、React local state、Worker 运行中任务写进存档。

## 四、核心数据模型

### 1. `GameState`

`GameState` 是唯一规则数据源，必须可序列化、可校验、可迁移。本文只保留架构摘要；字段权威定义以 [10_数据结构与存档方案.md](./10_数据结构与存档方案.md) 为准，避免同一 schema 在多份文档中分叉。

```ts
type GameState = {
  schemaVersion: number;
  gameId: string;
  seed: string;
  turn: number;
  phase: TurnPhase;
  activePlayerId: PlayerId;
  rngState: RngState;
  map: MapState;
  players: Record<PlayerId, PlayerState>;
  cities: Record<CityId, CityState>;
  units: Record<UnitId, UnitState>;
  tech: TechState;
  diplomacy: DiplomacyState;
  victory: VictoryState;
  eventLog: GameEvent[];
  commandLog: CommandRecord[];
};
```

| 字段 | 说明 | 第一版要求 |
| --- | --- | --- |
| `schemaVersion` | 存档结构版本 | 必须有，读档时用于迁移。 |
| `seed` / `rngState` | 地图和随机事件确定性来源 | 所有随机结果必须来自可记录 RNG。 |
| `phase` | 当前回合阶段 | 用于限制可执行 Command。 |
| `map` | 地块、地形、资源、可见性 | 不保存渲染坐标，只保存逻辑坐标。 |
| `players` | 玩家资源、科技、文明特性、AI 状态 | AI 和人类玩家共用结构。 |
| `cities` | 城市人口、产出、建筑、生产队列 | 城市是局部资源结算核心。 |
| `units` | 单位位置、血量、移动力、命令状态 | 单位不保存 Sprite 引用。 |
| `eventLog` | 可展示事件 | 用于日志和复盘，不替代状态。 |
| `commandLog` | 可重放命令 | 用于未来回放和 bug 复现。 |

### 2. 地图状态

```ts
type MapState = {
  kind: "square" | "hex";
  width: number;
  height: number;
  tiles: Record<TileId, TileState>;
};

type TileState = {
  id: TileId;
  coord: GridCoord;
  terrain: TerrainType;
  feature?: FeatureType;
  resource?: ResourceType;
  ownerId?: PlayerId;
  cityId?: CityId;
  unitIds: UnitId[];
  exploredBy: PlayerId[];
  visibleBy: PlayerId[];
};
```

第一版建议 `kind = "square"`，更快验证原型；如果后续决定转六边形，坐标接口保持抽象，避免全项目散落 `x + y * width` 这类计算。

### 3. UI 状态

UI 状态不进入 `GameState`，单独放在 `UIState`。

```ts
type UIState = {
  selectedTileId?: TileId;
  selectedUnitId?: UnitId;
  selectedCityId?: CityId;
  hoveredTileId?: TileId;
  openPanel?: "city" | "tech" | "diplomacy" | "victory" | "debug";
  camera: CameraState;
  overlays: OverlayState;
};
```

| 状态 | 存放位置 | 原因 |
| --- | --- | --- |
| 单位血量、移动力 | `GameState` | 属于规则。 |
| 当前选中单位 | `UIState` | 属于界面选择。 |
| 相机缩放和平移 | `UIState`，可选保存到设置 | 不影响规则结果。 |
| Tooltip 展开状态 | `UIState` | 不进存档。 |
| 调试 overlay 开关 | `UIState` 或 LocalStorage | 属于开发者偏好。 |

## 五、Command 模型

Command 分为三类，只有 `RuleCommand` 会进入可重放的 `CommandLog`。

| 类型 | 示例 | 是否进入 Replay CommandLog | 说明 |
| --- | --- | --- | --- |
| `RuleCommand` | 移动、建城、研究、生产、攻击、宣战、结束回合。 | 是 | 改变 `GameState` 的唯一外部入口。 |
| `UIIntent` | 选中单位、hover 地块、打开城市面板、移动相机。 | 否 | 只改变 `UIState`，不影响规则结果。 |
| `DebugCommand` | 跳回合、触发胜利、导入坏档测试、显示全知视角。 | 默认否；需要时写入 DebugLog | 仅开发模式可用，不参与正式回放。 |

玩家、AI、系统自动结算都使用 `RuleCommand` 或 Simulation 内部 Action 表达。UI 和调试工具不能绕过 `Validator` 修改规则状态。

### 1. RuleCommand 基础结构

```ts
type RuleCommand<TType extends RuleCommandType = RuleCommandType, TPayload = unknown> = {
  id: string;
  type: TType;
  actorId: PlayerId | "system";
  turn: number;
  phase: TurnPhase;
  createdAt: number;
  payload: TPayload;
  clientMeta?: {
    source: "player" | "ai" | "tutorial" | "debug";
    reason?: string;
    traceId?: string;
  };
};
```

### 2. 第一版 RuleCommand 清单

| Command | Payload | 发起方 | Validator 重点 |
| --- | --- | --- | --- |
| `MOVE_UNIT` | `unitId`, `toTileId`, `path?` | 玩家/AI | 是否属于行动方、路径可达、移动力足够、目标地块可进入。 |
| `FOUND_CITY` | `unitId`, `tileId`, `cityName` | 玩家/AI | 单位类型、地块条件、城市距离、玩家城市上限。 |
| `SET_CITY_PRODUCTION` | `cityId`, `itemId` | 玩家/AI | 城市归属、生产项是否解锁、资源是否满足。 |
| `CHOOSE_TECH` | `techId` | 玩家/AI | 前置科技、是否已完成、是否正在研究。 |
| `DECLARE_WAR` | `targetPlayerId` | 玩家/AI | 外交状态、冷却、代价。 |
| `ATTACK_UNIT` | `attackerId`, `defenderId` | 玩家/AI | 距离、可见性、攻击次数、战争状态。 |
| `END_TURN` | 无 | 玩家/AI/System | 必要行动是否已处理，是否允许强制结束。 |
| `SAVE_GAME` | `slotId` | 玩家/System | 当前状态是否可保存。 |
| `LOAD_GAME` | `slotId` | 玩家 | 存档版本是否可迁移。 |

### 3. 第一版 UIIntent 清单

| UIIntent | Payload | 存放位置 |
| --- | --- | --- |
| `SELECT_UNIT` | `unitId` | `UIState.selectedUnitId` |
| `SELECT_CITY` | `cityId` | `UIState.selectedCityId` |
| `HOVER_TILE` | `tileId` | `UIState.hoveredTileId` |
| `OPEN_PANEL` | panel id | `UIState.openPanel` |
| `SET_CAMERA` | camera x/y/zoom | `UIState.camera` |

### 4. ValidationResult

```ts
type ValidationResult =
  | { ok: true; normalizedCommand: RuleCommand }
  | {
      ok: false;
      code: ValidationErrorCode;
      message: string;
      detail?: Record<string, unknown>;
    };
```

验证失败必须能被 UI 直接解释，例如：

| 错误码 | 展示文案 |
| --- | --- |
| `NOT_ENOUGH_MOVEMENT` | 移动力不足。 |
| `TILE_BLOCKED` | 目标地块无法进入。 |
| `TECH_PREREQ_MISSING` | 前置科技尚未完成。 |
| `CITY_LIMIT_REACHED` | 第一版每方最多 3 座城市。 |
| `NOT_OWNER` | 你不能操作不属于你的对象。 |

### 5. Command 执行原则

| 原则 | 要求 |
| --- | --- |
| 单入口 | 所有规则变更都经过 `CommandBus -> Validator -> Simulation`。 |
| 可记录 | 每个成功 `RuleCommand` 写入 `commandLog`。 |
| 可解释 | 成功和失败都产生可展示事件或错误。 |
| 可重放 | 同一初始 seed + 同一 CommandLog 应得到同一结果。 |
| 可回滚预留 | 第一版不必做完整 undo，但 Command 结构要便于未来调试回退。 |

## 六、单回合流程

第一版采用固定回合顺序，降低调试成本。这里是唯一权威回合状态机；[09_玩法规则规格表.md](./09_玩法规则规格表.md)、[10_数据结构与存档方案.md](./10_数据结构与存档方案.md)、[21_回合计算性能与调度方案.md](./21_回合计算性能与调度方案.md) 都应引用这组阶段。

| 顺序 | 阶段 | 处理内容 | 输出 |
| --- | --- | --- | --- |
| 1 | `PLAYER_ACTION` | 玩家移动单位、设置生产、选择科技、建城、攻击、查看外交。 | 成功 `RuleCommand`、即时事件。 |
| 2 | `PLAYER_END` | 玩家提交 `END_TURN`，系统检查未处理提醒并允许强制结束。 | 阶段锁定，禁止继续提交玩家规则命令。 |
| 3 | `AI_PLAN` | AI 基于玩家行动后的当前状态生成候选 `RuleCommand`。 | AI 意图、候选评分、耗时 trace。 |
| 4 | `AI_ACTION` | 主线程按固定顺序验证并执行 AI `RuleCommand`。 | AI 行动事件、被拒命令日志。 |
| 5 | `TURN_RESOLVE` | 对所有玩家按固定顺序结算城市产出、人口、生产、科技、维护费、单位状态。 | ResourceDelta、ProductionEvent、TechEvent、MaintenanceEvent。 |
| 6 | `WORLD_RESOLVE` | 战争迷雾刷新、胜利检测、回合上限检测、轻量世界事件。 | VictoryEvent、WorldEvent。 |
| 7 | `AUTOSAVE` | 在完整稳定状态上写入 `autosave_latest`。 | SAVE_COMPLETED 或 SAVE_FAILED。 |
| 8 | `NEXT_TURN` | 回合数 +1，刷新玩家输入阶段，进入下一回合。 | 新回合提示。 |

### 单回合伪代码

```ts
function endTurn(state: GameState, command: EndTurnCommand): SimulationResult {
  let result = applyCommand(state, command);
  const aiPlan = requestAiPlan(result.state);
  for (const aiCommand of aiPlan.commands) {
    result = tryApplyCommand(result.state, aiCommand, result.events);
  }
  result = resolveTurnForAllPlayers(result.state);
  result = resolveWorld(result.state);
  result = autosaveStableState(result.state);
  return startNextTurn(result.state, result.events);
}
```

真实实现中，Worker 请求是异步的；UI 应在 `AI_PLAN` 阶段显示“AI 思考中”，但相机拖拽、日志查看、面板浏览不能卡住。

## 七、坐标系统

坐标系统必须从第一版就抽象清楚，否则后续从方格切到六边形会非常痛。

### 1. 坐标类型

```ts
type GridCoord =
  | { kind: "square"; x: number; y: number }
  | { kind: "hex"; q: number; r: number };

type WorldPoint = { x: number; y: number };
type ScreenPoint = { x: number; y: number };
```

| 坐标 | 用途 | 归属 |
| --- | --- | --- |
| `GridCoord` | 规则层地图坐标 | GameState、Simulation、Pathfinding |
| `WorldPoint` | PixiJS 世界坐标 | RenderEngine |
| `ScreenPoint` | 浏览器屏幕坐标 | InputController、React Overlay |

### 2. 坐标转换接口

```ts
type CoordinateSystem = {
  tileToWorld(coord: GridCoord): WorldPoint;
  worldToTile(point: WorldPoint): GridCoord | null;
  screenToWorld(point: ScreenPoint, camera: CameraState): WorldPoint;
  getNeighbors(coord: GridCoord): GridCoord[];
  distance(a: GridCoord, b: GridCoord): number;
};
```

### 3. 第一版坐标决策

| 问题 | 决策 |
| --- | --- |
| 第一版地图形态 | 方格已定，保留六边形接口作为第二版迁移目标。 |
| 点击命中 | 第一版用 CPU 坐标换算，不做 GPU Picking。 |
| 寻路 | 使用 `CoordinateSystem.getNeighbors`，不要直接写死四方向或六方向。 |
| 地图边界 | 规则层统一判断，渲染层只负责表现。 |
| 城市范围 | 通过坐标距离计算，不依赖屏幕像素。 |

## 八、React 与 PixiJS 同步策略

React 和 PixiJS 必须分层。React 管复杂 UI，PixiJS 管地图画面，两者通过状态订阅和 Command 交互。

### 1. 状态分层

| 状态 | 所在层 | 示例 |
| --- | --- | --- |
| 规则状态 | `GameStateStore` | 单位位置、城市产出、科技进度、战争状态。 |
| UI 状态 | `UIStateStore` | 选中对象、打开面板、相机、hover。 |
| 渲染缓存 | `RenderEngine` 内部 | Sprite 池、Texture、Container、Graphics。 |
| 组件状态 | React 组件内部 | 输入框临时值、展开折叠状态。 |

### 2. 同步方式

| 同步点 | 策略 |
| --- | --- |
| GameState -> React | 使用 selectors 派生面板数据，避免组件读整棵状态树。 |
| GameState -> PixiJS | RenderEngine 接收状态 diff，更新 Tile/Unit/Overlay 容器。 |
| React -> GameState | React 只 dispatch Command，不直接 set GameState。 |
| PixiJS -> GameState | PixiJS 交互事件转为 Command 或 UIState 变更。 |
| Camera -> React Overlay | 相机变化写入 UIState，DOM Tooltip/浮层按坐标转换定位。 |

### 3. 渲染更新建议

| 内容 | 更新策略 |
| --- | --- |
| 地形 Tile | 地图生成后基本静态，使用批处理或 Sprite 池。 |
| 资源图标 | 资源变化少，按 Tile diff 更新。 |
| 单位 Sprite | 按 `unitId` 建立映射，位置变化时移动 Sprite。 |
| 战争迷雾 | 第一版可用 overlay alpha；后续升级 Shader。 |
| 选中高亮 | 来自 UIState，变化频繁但对象少。 |
| 路径预览 | hover/选中时计算并绘制，注意节流。 |
| 调试坐标层 | 开发模式开启，避免常驻影响性能。 |

### 4. 事件边界

| 事件来源 | 处理方式 |
| --- | --- |
| 点击地图格 | `InputController` 计算 tileId，更新 hover/selection 或提交移动 Command。 |
| 点击单位 | 更新 `selectedUnitId`，打开单位信息面板。 |
| 点击城市 | 更新 `selectedCityId`，打开城市面板。 |
| 点击 DOM 按钮 | 直接 dispatch 对应 Command。 |
| 右键目标地块 | 如果有选中单位，生成 `MOVE_UNIT` Command。 |
| 滚轮 | 更新 CameraState，不进入 CommandLog。 |

## 九、Worker 通信协议

Worker 用于耗时但可独立计算的任务：AI 决策、寻路、地图生成、胜利评估。第一版可以先让部分任务在主线程跑，但接口要按 Worker 设计。

### 1. 请求/响应格式

```ts
type WorkerRequest<TPayload = unknown> = {
  requestId: string;
  type: WorkerRequestType;
  schemaVersion: number;
  createdAt: number;
  payload: TPayload;
};

type WorkerResponse<TPayload = unknown> =
  | {
      requestId: string;
      ok: true;
      type: WorkerRequestType;
      durationMs: number;
      payload: TPayload;
    }
  | {
      requestId: string;
      ok: false;
      type: WorkerRequestType;
      durationMs: number;
      error: {
        code: string;
        message: string;
        detail?: Record<string, unknown>;
      };
    };
```

### 2. 第一版 Worker 请求类型

| 类型 | 输入 | 输出 | 备注 |
| --- | --- | --- | --- |
| `GENERATE_MAP` | seed、尺寸、地图规则 | `MapState` | 可先主线程实现，接口预留。 |
| `FIND_PATH` | 单位、起点、终点、地图通行数据 | 路径、成本、是否可达 | 鼠标 hover 高频时需要节流或缓存。 |
| `AI_PLAN_TURN` | `AIReadableState` | Command 候选列表、AI 意图 | 必须在主线程再次验证。 |
| `EVALUATE_VICTORY` | 当前局势 | 胜利进度评分 | 第一版可放主线程，后续移出。 |

### 3. 通信约束

| 约束 | 要求 |
| --- | --- |
| 可序列化 | Payload 必须可结构化克隆，不能传函数、DOM、PixiJS 对象。 |
| requestId | 每个请求必须有唯一 ID，用于匹配响应和丢弃过期结果。 |
| 超时 | AI 和寻路请求需要超时策略，超时后使用保守行为。 |
| 取消 | 高频路径预览需要取消或忽略旧请求。 |
| 错误 | Worker 错误必须写入 Debug Event，不让页面静默失败。 |
| 状态裁剪 | Worker 只拿必要数据，避免频繁复制整棵 GameState。 |

### 4. AI 输出示例

```ts
type AiPlanResponse = {
  playerId: PlayerId;
  intent: {
    goal: "expand" | "defend" | "attack" | "research" | "economy";
    targetTileId?: TileId;
    targetPlayerId?: PlayerId;
    reason: string;
    score: number;
  };
  commands: Command[];
};
```

AI 不直接改状态，这点必须坚持。否则存档、回放、调试都会变得混乱。

## 十、可重放与确定性设计

策略游戏需要能复现 bug，也需要未来支持复盘。第一版不必做完整录像系统，但状态和随机数要从第一天就按可重放设计。

### 1. 确定性原则

| 方向 | 要求 |
| --- | --- |
| 随机数 | 所有随机结果都来自带 seed 的 RNG，不直接调用 `Math.random()`。 |
| 时间 | 规则不依赖真实时间；`createdAt` 只用于日志和调试，不参与结算。 |
| 顺序 | 同一阶段内的结算顺序固定，例如城市按 `cityId` 排序。 |
| 浮点 | 规则数值尽量使用整数或固定小数，避免渲染帧率影响规则。 |
| Worker | Worker 输出 Command，主线程按固定顺序验证执行。 |
| 存档 | 保存 `rngState`、`turn`、`phase`、GameState 快照。 |

### 2. CommandLog 与 EventLog 区别

| 日志 | 用途 | 是否用于重放 |
| --- | --- | --- |
| `CommandLog` | 记录改变规则状态的 `RuleCommand`，例如移动、研究、结束回合。 | 是，未来从初始 seed 重放。 |
| `EventLog` | 记录结果事件，例如粮食 +2、科技完成、单位死亡。 | 否，主要用于展示和校验。 |

### 3. 重放策略

| 阶段 | 方案 |
| --- | --- |
| 第一版 | 保存完整 GameState 快照 + 最近事件日志，支持读档。 |
| 调试增强 | 支持导出 seed、GameState、CommandLog、EventLog。 |
| 第二版 | 从初始 seed + CommandLog 重建整局，用 EventLog 做校验。 |

### 4. 需要避免的非确定性

| 风险 | 规避方式 |
| --- | --- |
| AI 根据当前时间做选择 | AI 评分只读 GameState 和 RNG。 |
| 遍历对象 key 顺序不稳定 | 对城市、单位、玩家 ID 显式排序。 |
| 渲染动画触发规则 | 动画只表现结果，规则先结算。 |
| Worker 返回顺序不同 | 用 requestId 和 turn 校验，只接收当前阶段结果。 |
| 浮点误差影响战斗 | 战斗公式使用整数攻击、防御、血量。 |

## 十一、存档与 Storage 边界

### 1. SaveGame 结构

```ts
type SaveGame = {
  saveId: string;
  schemaVersion: number;
  buildVersion: string;
  savedAt: number;
  label: string;
  preview: {
    turn: number;
    playerName: string;
    mapSize: string;
    victoryProgress: string;
  };
  state: GameState;
};
```

### 2. 存档规则

| 项目 | 决策 |
| --- | --- |
| 技术 | IndexedDB 保存存档，LocalStorage 保存音量、调试开关等设置。 |
| 自动存档 | 每次玩家结束回合后自动保存一个 `autosave`。 |
| 手动存档 | 第一版至少支持一个手动槽位。 |
| 版本迁移 | `schemaVersion` 小于当前版本时走 migrate。 |
| 存档校验 | 读档时校验关键字段，失败给出明确错误。 |
| 调试导出 | 支持导出 JSON，方便复现 bug。 |

## 十二、EventLog 设计

EventLog 既给玩家解释结果，也给开发者定位问题。

### 1. 事件结构

```ts
type GameEvent = {
  id: string;
  turn: number;
  phase: TurnPhase;
  type: GameEventType;
  severity: "info" | "warning" | "error" | "debug";
  actorId?: PlayerId | "system";
  entityIds?: string[];
  message: string;
  data?: Record<string, unknown>;
};
```

### 2. 第一版事件类型

| 类型 | 示例 |
| --- | --- |
| `RESOURCE_DELTA` | 首都本回合粮食 +3、生产力 +2。 |
| `PRODUCTION_PROGRESS` | 工坊完成度 8/20。 |
| `PRODUCTION_COMPLETE` | 首都完成侦察兵。 |
| `TECH_PROGRESS` | 陶器研究 +4。 |
| `TECH_COMPLETE` | 已完成弓术研究。 |
| `UNIT_MOVED` | 侦察兵移动到 x=4, y=3。 |
| `COMBAT_RESOLVED` | 战士攻击弓手，造成 35 伤害。 |
| `AI_INTENT` | AI 当前目标：扩张到东部资源点。 |
| `VICTORY_PROGRESS` | 科技胜利进度 3/8。 |
| `VALIDATION_FAILED` | 移动力不足。 |
| `DEBUG_PERFORMANCE` | 本回合 AI 用时 42ms。 |

### 3. 日志展示分层

| 面向对象 | 展示内容 |
| --- | --- |
| 玩家日志 | 资源、生产、科技、战斗、胜利进度。 |
| Tooltip | 当前操作失败原因、地块收益、单位状态。 |
| 调试日志 | AI 意图、Worker 用时、Command、Validator 结果。 |
| 复盘面板 | 关键回合、胜利/失败原因、分数来源。 |

## 十三、调试与测试接口

第一版必须把调试能力当成核心功能，不然后续数值和 AI 很难调。

| 工具 | 数据来源 | 作用 |
| --- | --- | --- |
| FPS 面板 | RenderEngine 性能计数 | 观察缩放、战争迷雾、单位数量带来的掉帧。 |
| 坐标层 | CoordinateSystem | 验证点击命中、寻路、城市范围。 |
| 回合日志 | EventLog | 解释资源和科技为什么变化。 |
| RuleCommand Inspector | CommandLog | 检查玩家和 AI 规则动作是否符合预期。 |
| AI 意图面板 | AI Worker 响应 | 判断 AI 是设计问题还是实现问题。 |
| 存档导出 | StorageService | 复现 bug。 |
| 固定地图种子 | MapGenerator | 对比不同数值版本。 |

推荐测试分层：

| 测试类型 | 覆盖内容 |
| --- | --- |
| Simulation 单元测试 | 资源结算、移动合法性、科技完成、胜利检测。 |
| Validator 单元测试 | 非法移动、前置科技缺失、城市上限、归属错误。 |
| Replay 测试 | 同一 seed + CommandLog 得到同一 GameState 摘要。 |
| Worker 测试 | AI 输出格式、寻路结果、超时错误处理。 |
| Playwright 冒烟测试 | 加载页面、显示地图、移动单位、结束回合、保存读档。 |
| 性能测试 | 20x20 地图、20 个单位、战争迷雾开启时仍保持目标帧率。 |

## 十五、风险清单

| 风险 | 表现 | 影响 | 预防方案 |
| --- | --- | --- | --- |
| GameState 被 UI/渲染随意修改 | 状态来源混乱，存档和回放不可信。 | 高 | 所有规则变化必须走 CommandBus。 |
| React 和 PixiJS 各存一份规则状态 | 单位位置、选中状态、面板数据不一致。 | 高 | 规则状态唯一，渲染只做缓存。 |
| Worker 直接返回新 GameState | AI 绕过验证，难以解释和复现。 | 高 | Worker 只返回 Command 候选和意图。 |
| 随机数不可控 | bug 无法复现，回放不一致。 | 高 | 禁止规则层直接使用 `Math.random()`。 |
| 回合结算顺序不固定 | 同一局不同运行结果不同。 | 高 | 所有结算顺序显式排序并写测试。 |
| 坐标计算散落各处 | 后续换六边形或修命中会大面积改代码。 | 中高 | 统一 `CoordinateSystem`。 |
| 纯 UI 组件承担规则逻辑 | 面板越做越难维护。 | 中高 | 规则放 Simulation，UI 只 dispatch Command。 |
| EventLog 过于粗略 | 玩家不知道为什么输，开发者也难调。 | 中 | 第一版就记录资源、生产、科技、AI 意图。 |
| 存档无版本号 | 后续字段变化导致旧存档坏掉。 | 中 | SaveGame 必须带 `schemaVersion`。 |
| 高频路径预览卡顿 | 鼠标移动时不断寻路导致主线程掉帧。 | 中 | 节流、缓存、Worker、忽略旧请求。 |
| PixiJS 对象泄漏 | 切换地图或读档后内存上涨。 | 中 | Sprite 池和销毁策略，读档时重建渲染缓存。 |
| 调试工具后置 | AI、数值、存档问题难定位。 | 中 | 调试面板进入第一版必做范围。 |
| 过早抽象完整引擎 | 第一版迟迟不能验证玩法。 | 中 | 只抽象边界，不提前写通用大框架。 |

## 十六、第一版工程验收清单

| 验收项 | 标准 |
| --- | --- |
| 状态 | `GameState` 能完整表达 12x12 到 20x20 地图、1 玩家 + 1 AI、城市、单位、科技、胜利进度。 |
| 命令 | 移动、建城、生产、研究、攻击、结束回合都通过 Command。 |
| 验证 | 非法操作有明确错误码和中文提示。 |
| 回合 | 结束回合后按固定顺序完成资源、生产、科技、AI、胜利检测。 |
| 渲染 | PixiJS 根据状态绘制地图、单位、资源、战争迷雾、选中高亮。 |
| UI | React 面板能显示城市、科技、胜利、日志、调试信息。 |
| Worker | AI 或寻路至少一个模块按 Worker 协议接入，或有同协议主线程 fallback。 |
| 存档 | IndexedDB 能保存和读取当前局，刷新页面后恢复。 |
| 日志 | EventLog 能解释每回合主要变化。 |
| 可复现 | 固定 seed + 固定操作能得到一致结果。 |
| 调试 | 能导出 GameState、CommandLog、EventLog JSON。 |

## 十七、推荐实现顺序

| 顺序 | 工作 | 原因 |
| --- | --- | --- |
| 1 | 定义 `GameState`、ID、坐标、配置表类型。 | 先稳住数据结构。 |
| 2 | 实现 Command、Validator、Simulation 最小链路。 | 先让规则闭环可测试。 |
| 3 | 接入 PixiJS 地图和坐标命中。 | 验证 WebGL 地图体验。 |
| 4 | 接入 React 城市/科技/日志面板。 | 验证 DOM UI 分层。 |
| 5 | 实现结束回合和 EventLog。 | 让 30 回合循环跑起来。 |
| 6 | 接入 AI Worker 或同协议 fallback。 | 验证对手压力和后台计算边界。 |
| 7 | 接入 IndexedDB 存档。 | 验证 GameState 可序列化和迁移预留。 |
| 8 | 加调试面板、固定种子、导出工具。 | 支撑后续玩法和数值调研。 |
