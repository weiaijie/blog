# 21 回合计算性能与调度方案

## 一、为什么必须单独考虑

文明类/4X 游戏的卡顿不只来自 WebGL 渲染。每次点击“结束回合”时，规则层会集中处理资源、城市、科技、单位、AI、视野、胜利检测、日志和存档。如果这些计算都同步挤在主线程里，玩家会感觉页面冻结。

因此第一版必须把“每回合计算效率”作为独立性能对象，而不是只看 FPS。

## 二、回合计算范围

| 阶段 | 主要计算 | 卡顿风险 | 第一版策略 |
| --- | --- | --- | --- |
| Command 校验 | 移动、攻击、生产、研究、结束回合是否合法 | 低 | 主线程同步执行，并记录耗时 |
| 玩家经济结算 | 城市产出、人口增长、生产队列、科技推进、维护费 | 中 | 主线程同步执行，按城市/玩家分段 trace |
| AI 局势分析 | 读取地图、城市、单位、资源、威胁、胜利进度 | 中到高 | 第一版可同步，接口按 Worker 设计 |
| AI 决策评分 | 扩张、研究、生产、单位行动、宣战评分 | 中到高 | 超预算后迁移 Worker |
| 寻路 | 单位路径、AI 路线、路径预览 | 中到高 | 玩家路径可同步；AI 批量寻路优先 Worker |
| 战斗结算 | 伤害、防御、死亡、占城 | 低到中 | 主线程同步执行 |
| 视野/战争迷雾 | 根据单位/城市刷新可见地块 | 中 | 第一版 dirty update，避免每次全图重算 |
| 胜利检测 | 征服、科技、分数、回合上限 | 低 | 主线程同步执行 |
| EventLog 生成 | 资源、生产、科技、AI 意图、战斗、胜利日志 | 中 | 限制日志数量，长日志延后压缩 |
| 自动存档 | 保存 GameState、CommandLog、EventLog 摘要 | 中到高 | 放到回合结束后异步执行，失败不阻塞当前局 |

## 三、回合计算 trace 结构

每次结束回合都生成 `TurnTrace`，用于 Debug Panel、Debug Export 和性能回归。

```ts
type TurnTrace = {
  turn: number;
  activePlayerId: string;
  startedAt: number;
  endedAt: number;
  totalDurationMs: number;
  phases: TurnTracePhase[];
  commandCount: number;
  eventCount: number;
  aiCommandCount: number;
  rejectedAiCommandCount: number;
  saveScheduled: boolean;
  warnings: string[];
};

type TurnTracePhase = {
  phase:
    | "validateEndTurn"
    | "playerEconomy"
    | "aiPlan"
    | "aiCommands"
    | "aiEconomy"
    | "vision"
    | "victory"
    | "eventLog"
    | "autosave";
  durationMs: number;
  itemCount?: number;
  details?: Record<string, unknown>;
};
```

## 四、第一版预算目标

这些数字是**预算目标**，不是已验证性能。必须由本地原型通过 `performance.mark()` / `performance.measure()`、Debug Panel 和浏览器 Performance 工具确认。

| 阶段 | 目标 | 最低可接受 | 超预算处理 |
| --- | ---: | ---: | --- |
| 总结束回合耗时 | 500ms 内 | 1000ms 内 | 分析 TurnTrace，拆分 AI/寻路/存档 |
| Command 校验 | 20ms 内 | 50ms 内 | 检查 Validator 是否做了全图扫描 |
| 玩家经济结算 | 50ms 内 | 100ms 内 | 按城市增量更新，避免全局重算 |
| AI 局势分析 | 100ms 内 | 250ms 内 | 裁剪 AIReadableState，迁移 Worker |
| AI 决策评分 | 200ms 内 | 550ms 内 | 降低候选数量、缓存评分、迁移 Worker |
| AI Command 执行 | 100ms 内 | 200ms 内 | 限制每回合 AI 行动数量 |
| 视野刷新 | 50ms 内 | 120ms 内 | dirty tiles、按单位视野增量更新 |
| 胜利检测 | 20ms 内 | 50ms 内 | 缓存胜利进度派生值 |
| EventLog 生成 | 20ms 内 | 50ms 内 | 限制长日志和批量事件 |
| 自动存档调度 | 20ms 内 | 50ms 内 | 只调度，不同步等待 IndexedDB 写入 |

## 五、调度策略

| 任务 | 主线程同步 | Worker | idle/异步 |
| --- | --- | --- | --- |
| Command 校验 | 是 | 否 | 否 |
| 玩家经济结算 | 是 | 第二版可评估 | 否 |
| AI 局势分析 | 第一版可同步 | 推荐预留 | 否 |
| AI 决策评分 | 简单 AI 可同步 | 复杂后迁移 | 否 |
| 寻路 | 单次玩家路径同步 | 批量 AI 寻路推荐 | 可缓存 |
| 视野刷新 | 小地图同步 | 大地图可 Worker | 否 |
| 自动存档 | 否 | 否 | 是，IndexedDB Promise |
| Debug Export | 否 | 可选 | 是，用户主动触发 |
| 日志压缩 | 否 | 可选 | 是 |

## 六、避免每回合变慢的规则

| 规则 | 说明 |
| --- | --- |
| 不做无差别全图扫描 | 资源结算按城市，视野按单位/城市，胜利进度按变更项更新。 |
| AI 使用裁剪状态 | Worker 或 AI 不读取完整 UI/render 状态，只读取 AIReadableState。 |
| 限制 AI 候选数量 | 第一版不要让 AI 对每个地块、每个单位、每个科技做全组合搜索。 |
| 每阶段都 trace | 没有 trace 的阶段不允许进入“优化完成”。 |
| 存档不阻塞回合 | 自动存档失败只提示，不回滚当前回合。 |
| 日志有保留策略 | EventLog 保留最近 N 回合详细日志，旧日志转摘要。 |
| Debug 功能可关闭 | Debug overlay 不参与正式性能判断。 |

## 七、Turn Profiler 面板

Debug Panel 需要增加 `Turn Profiler` 页签。

| 字段 | 用途 |
| --- | --- |
| totalDurationMs | 本次结束回合总耗时 |
| slowestPhase | 最慢阶段 |
| phaseTable | 每个阶段的耗时、itemCount、warning |
| aiDurationMs | AI 总耗时 |
| pathfindingDurationMs | 寻路总耗时 |
| economyDurationMs | 经济结算耗时 |
| visionDurationMs | 视野刷新耗时 |
| eventCount | 本回合生成事件数量 |
| commandCount | 本回合执行命令数量 |
| autosaveDurationMs | 自动存档实际写入耗时 |
| warnings | 超预算、Worker 超时、存档失败等 |

## 八、性能测试用例

| 用例 | 场景 | 需要记录 |
| --- | --- | --- |
| 默认局第 1 回合 | 1 城、2 单位、少量可见地块 | TurnTrace、frame time |
| 默认局第 15 回合 | 2 城、若干单位、AI 已接触 | AI、视野、经济耗时 |
| 默认局第 30 回合 | 胜利/分数检测 | 胜利检测、复盘生成耗时 |

| 存档压力局 | EventLog 较长、CommandLog 较长 | autosave 调度和 IndexedDB 写入耗时 |

## 十、资料来源

- MDN Performance API：可用 `PerformanceMark`、`PerformanceMeasure` 等记录自定义性能测量，Performance API 也可在 Worker 中使用。  
  https://developer.mozilla.org/en-US/docs/Web/API/Performance_API

- MDN PerformanceObserver：可监听性能条目。  
  https://developer.mozilla.org/en-US/docs/Web/API/PerformanceObserver

- MDN Web Workers：后台线程可用于独立脚本计算，适合作为 AI/寻路/地图生成的迁移方向。  
  https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API

- MDN requestIdleCallback：可在主线程空闲时调度低优先级后台任务，但不能作为关键回合结算的可靠实时机制。  
  https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback

## 十一、结论

每回合计算性能必须和渲染性能并列管理。第一版不需要过度优化，但必须做到：

- 每个回合阶段都有 trace。
- AI、寻路、视野、存档这些高风险阶段有独立耗时。
- 超预算时知道慢在哪里。
- Worker 迁移有清晰边界。
- 自动存档和 Debug Export 不阻塞回合推进。
