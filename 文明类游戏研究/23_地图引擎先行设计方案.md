# 23 地图引擎先行设计方案

## 一、结论

地图开发不能直接从“画一张地图”开始。正确顺序应该是：

1. 先做地图引擎设计。
2. 再做地图引擎骨架。
3. 再做最小地图渲染。
4. 最后再做正式地图内容和玩法地图。

原因很简单：如果第一版先把 16x16/20x20 地图做成全量 Sprite 平铺，后面再改 chunk/culling/streaming，会牵动相机、坐标、点击命中、迷雾、路径、调试、存档、AI，可维护性会变差。

## 二、地图引擎必须先确定的边界

| 边界 | 决策 |
| --- | --- |
| 地图数据 | 全图存在 `GameState.map.tiles`，规则层永远可以读全图。 |
| 渲染对象 | PixiJS scene graph 只挂载 active render area 内的 tile/chunk。 |
| 相机 | 相机只管理 world/screen transform，不直接决定规则状态。 |
| chunk | 第一版就有 `ChunkManager`，哪怕地图默认只有 16x16。 |
| culling | 第一版就有 viewport + 50% overscan。 |
| 对象池 | 第一版就有 `TilePool` / `SpritePool`，避免滑动时频繁创建销毁。 |
| 坐标系统 | 所有 grid/world/screen 转换集中到 `CoordinateSystem`。 |
| 命中 | 第一版 CPU 坐标命中，但必须通过统一接口。 |
| 迷雾 | 迷雾层跟随 chunk/tile active area 更新。 |
| Debug | Debug Render 面板必须显示 camera、viewport、active chunks、sprite count。 |

## 三、地图引擎模块

| 模块 | 职责 | 第一版是否必须 |
| --- | --- | --- |
| `MapDataProvider` | 从 GameState 读取 tile、resource、visibility、owner 数据。 | 必须 |
| `CoordinateSystem` | grid/world/screen 坐标转换，支持未来方格/六边形切换。 | 必须 |
| `CameraController` | 管理 pan/zoom、target camera、clamp、鼠标中心缩放。 | 必须 |
| `ViewportManager` | 根据 camera 计算 viewport、buffered viewport、active render area。 | 必须 |
| `ChunkManager` | 把地图拆成 chunk，决定挂载/卸载哪些 chunk。 | 必须 |
| `TilePool` | 复用 tile/resource/fog sprite。 | 必须 |
| `LayerManager` | terrain/resource/city/unit/fog/overlay/debug 分层。 | 必须 |
| `HitTestService` | screen point -> tile/unit/city 命中。 | 必须 |
| `FogRenderer` | 根据 visibility/explored 状态绘制迷雾。 | 必须 |
| `MapDebugOverlay` | 显示坐标、chunk、active area、AI 目标、路径。 | 必须 |

## 四、推荐实现顺序

| 阶段 | 任务 | 验收 |
| --- | --- | --- |
| E0 | 定义接口：`RenderEngine`、`CoordinateSystem`、`CameraState`、`ViewportManager`。 | 无 PixiJS 也能单测坐标和 viewport。 |
| E1 | PixiJS 初始化和 layer tree。 | 空 canvas 能 resize，Debug 显示 renderer。 |
| E2 | 实现 chunk 切分和 active area 计算。 | camera 移动后 active chunk set 正确。 |
| E3 | 实现 TilePool 和 chunk mount/unmount。 | 滑动时复用 Sprite，不频繁 new/destroy。 |
| E4 | 接入 atlas tile 渲染。 | 16x16 地形能显示，active area 外不挂载。 |
| E5 | 接入 pan/zoom 和鼠标中心缩放。 | 平移缩放不改变规则坐标，命中准确。 |
| E6 | 接入资源、城市、单位、迷雾层。 | 每层都跟 chunk/active area 一致。 |
| E7 | 接入 overlay 和路径预览。 | 只渲染当前选择相关 overlay。 |
| E8 | 接入 Debug Render 面板。 | 能看到 active chunks、sprite count、viewport、overscan。 |
| E9 | 20x20 压力测试。 | 记录 FPS、p95、挂载/卸载次数、命中耗时。 |

## 五、第一版 chunk 策略

| 项 | 建议 |
| --- | --- |
| chunk 尺寸 | 8x8 或 10x10，先选 8x8 便于 16x16/32x32 切分。 |
| active area | viewport + 50% overscan。 |
| unload 策略 | 超出 active area 的 chunk 隐藏或 detach；Sprite 放回 pool。 |
| 挂载预算 | 每帧最多挂载 N 个 chunk/tile，避免突然卡顿。 |
| Debug 显示 | active chunk 用边框显示，unloaded chunk 不显示。 |
| 数据来源 | chunk 不保存规则状态，只缓存 tileId 列表和 Sprite 引用。 |

## 六、不能做的坏路径

| 坏路径 | 后果 |
| --- | --- |
| 先全量创建所有 tile Sprite | 20x20 没问题，但 32x32/64x64 重构成本高。 |
| tile Sprite 直接保存规则数据 | 存档、AI、回放和渲染耦合。 |
| 点击命中依赖 PixiJS Sprite 树遍历 | 大地图和多 overlay 后难控，命中规则不透明。 |
| 迷雾每次全图重建 | 地图扩大后结束回合变慢。 |
| Debug 坐标全图常开 | 文本对象会拖垮性能。 |
| 相机逻辑散落在 UI、Pixi、输入模块 | 后续面板遮挡、缩放中心、移动端手势都会难维护。 |

## 七、地图开发与玩法开发的关系

地图引擎先行不等于先做复杂大地图或 streaming。它的意思是：哪怕第一张可玩地图只有 16x16，也要用正确的引擎边界去渲染它。第一版必须有 `ViewportManager`、轻量 `ChunkManager`、`TilePool`、active area 统计和 Debug 字段；是否真正卸载视口外 Sprite 由 20x20 Spike 数据决定。

| 阶段 | 地图内容 | 引擎要求 |
| --- | --- | --- |
| 技术 Spike | 20x20 固定调试地图 | chunk/culling/overscan 必须工作 |
| MVP 地图 | 16x16 默认地图 | 资源、单位、迷雾、点击、路径、调试层可用 |
| 压力地图 | 20x20 上限地图 | 测挂载/卸载、FPS、命中、视野 |
| 第二版地图 | 32x32 | 扩展 chunk、cache texture、Worker 寻路/AI |
| 长期地图 | 64x64+ | 需要分区 AI、流式资源、大地图存档优化 |

## 八、验收清单

| 项 | 验收 |
| --- | --- |
| active area | camera 改变后 active chunks 正确变化。 |
| overscan | 视口外 50% 缓冲区内 tile 已挂载。 |
| unload | 远离视口的 chunk 会隐藏、detach 或回收到 pool。 |
| 无空白 | 连续拖拽不会看到未加载空白。 |
| 无全量依赖 | 渲染层不要求全图 Sprite 同时存在。 |
| 命中正确 | 缩放和平移后点击 tile/unit/city 准确。 |
| Debug 可见 | Debug 面板能显示 chunk 数、sprite 数、active area。 |
| 压力测试 | 20x20 地图下记录 FPS、p95、挂载次数、内存趋势。 |

## 九、结论

你的判断是对的：**地图引擎设计必须先于正式地图开发。**

第一版不应该做复杂大地图，但必须先做正确的地图引擎骨架：

- `CameraState`
- `CoordinateSystem`
- `ViewportManager`
- `ChunkManager`
- `TilePool`
- `LayerManager`
- `HitTestService`
- `MapDebugOverlay`

这样 16x16 的 MVP 地图不会变成未来 32x32/64x64 的技术债。
