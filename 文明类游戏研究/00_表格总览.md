# 00 表格总览

## 一、调研内容总览

| 模块 | 主要内容 | 设计意义 | 需要重点注意 |
| --- | --- | --- | --- |
| 类型定位 | 文明类游戏通常属于回合制 4X 策略游戏。4X 指探索、扩张、开发、冲突。 | 帮助确定游戏不是单纯战争游戏，而是长期文明经营。 | 不要只做征服，其他发展路线也要成立。 |
| 核心幻想 | 玩家从小聚落发展成强大文明，经历探索、建设、竞争和胜利。 | 提供玩家持续游玩的目标感。 | 要让玩家感觉自己的文明有成长历史，而不是纯数值膨胀。 |
| 探索 | 派单位揭开地图，发现资源、地形、遗迹、中立势力和其他文明。 | 制造开局不确定性和重开价值。 | 地图发现要影响后续策略，不能只是开视野。 |
| 扩张 | 建立新城市、控制土地、争夺关键资源点。 | 形成空间竞争和战略承诺。 | 扩张必须有代价，否则最优解会变成无限铺城。 |
| 开发 | 用人口、建筑、区域、资源、科技和经济提升文明能力。 | 让玩家把地图优势转化成长期实力。 | 开发系统要互相关联，避免变成独立菜单。 |
| 冲突 | 战争、外交压制、资源争夺、胜利条件竞争都属于冲突。 | 给玩家制造压力和对手感。 | 战争不能成为唯一正确答案。 |
| 地图系统 | 地形、资源、战争迷雾、随机地图、移动规则、防御加成。 | 地图是策略选择的基础。 | 地形和资源必须改变玩家决策。 |
| 城市系统 | 城市生产单位、建筑、科技、文化、金币，并通过人口成长扩大能力。 | 城市是文明发展的核心引擎。 | 城市数量、位置、专精方向都要有取舍。 |
| 资源系统 | 粮食、生产力、金币、科技、文化、战略资源、奢侈资源。 | 资源决定发展路线和冲突焦点。 | 稀缺资源要推动争夺和交易。 |
| 科技/制度树 | 科技解锁单位、建筑、资源、奇观或新规则；文化/制度解锁政策和政府。 | 提供长期规划和路线分化。 | 科技树不能只是奖励列表，要表达战略方向。 |
| 外交系统 | 交易、结盟、宣战、停战、边境开放、世界议会、外交胜利。 | 让其他文明不只是敌人。 | AI 动机要透明，否则外交会显得随机。 |
| 战争系统 | 单位、地形、城市攻防、补给、战争代价。 | 提供强冲突和地图控制手段。 | 降低无意义微操，强化战略代价。 |
| 胜利条件 | 常见有征服、科技、文化、外交、经济、分数胜利。 | 让玩家选择不同路线。 | 每种胜利都要有独特玩法，不只是换一个进度条。 |
| AI 系统 | AI 需要会发展、扩张、研究、作战、外交，并展示意图。 | 单人体验很依赖 AI。 | AI 不一定要完美，但要让玩家觉得合理。 |
| 新手引导 | 前 5 分钟引导玩家完成移动、建造、研究、结束回合和查看信息。 | 降低文明类游戏的上手门槛。 | 教学应嵌入回合流程，不要变成长说明书。 |
| 相机与操作手感 | 拖拽、缩放、选中、路径预览、地块高亮、快捷键。 | 地图游戏的手感直接影响体验。 | 操作反馈要快，缩放和平移不能卡顿。 |
| 地图编辑器/调试地图 | 提供固定测试地图、种子地图、资源布局查看。 | 原型阶段方便复现问题和调数值。 | 随机地图之外必须保留可复现测试场景。 |
| 事件系统 | 随机事件、时代事件、危机事件、外交事件。 | 给中后期制造变化，减少重复。 | 第一版只预留结构，不做复杂事件库。 |
| 教程/百科/悬浮提示 | 解释资源、科技、地形、单位、建筑、胜利条件。 | 把信息透明落成具体 UI 功能。 | Tooltip 要短，百科负责详细说明。 |
| 经济数值模型 | 每回合资源结算、人口增长、建筑收益、维护费、科技成本。 | 决定游戏是否可平衡。 | 第一版必须有可读的回合结算日志。 |
| 美术规格 | 地形、单位、建筑、资源图标、UI 图标、动效、字体。 | 防止后期资产返工。 | WebGL 地图优先使用图集思路。 |
| 音频反馈 | 回合结束、建造完成、科技完成、宣战、战斗、错误操作提示。 | 提升完成感和状态反馈。 | 第一版可先用少量占位音效。 |
| 测试指标 | 记录遇敌回合、每回合操作数、平均回合时长、胜利进度、重开率。 | 让“好不好玩”能被数据辅助判断。 | 原型阶段就要有事件日志。 |
| Web 平台定位 | 第一版定位为桌面浏览器 Web Demo，移动端只做兼容预留。 | 决定技术栈、UI 密度、输入和部署方式。 | 先利用 Web 快速发链接试玩。 |
| WebGL 渲染系统 | 用 WebGL 渲染地图、地形、单位、资源、战争迷雾、路径预览、动画。 | 保证地图缩放、拖拽、批量单位显示时仍然流畅。 | 不要把复杂 UI 全塞进 WebGL。 |
| DOM UI 分层 | 城市面板、科技树、外交面板、回合提示、Tooltip 用 DOM/前端框架。 | 提高复杂 UI 的开发效率和可维护性。 | 要处理 WebGL 坐标与 DOM 命中的转换。 |
| WebGPU 预留 | 渲染层保留抽象，未来可升级 WebGPU 或双后端。 | WebGPU 是更现代的 GPU API，但第一版不依赖。 | 第一版核心目标是稳定验证玩法。 |
| Web Worker | AI、寻路、地图生成、胜利评估等耗时任务放到 Worker。 | 避免主线程卡住，保证拖拽缩放顺畅。 | GameState 要轻量、可序列化。 |
| 本地存档 | 使用 IndexedDB 保存复杂存档，LocalStorage 只保存小配置。 | 支持中途退出、读档、复盘和测试。 | 存档内容围绕 GameState 设计。 |
| 部署发布 | 静态站点部署，资源带版本号，发链接即可试玩。 | Web 原型的优势是快速反馈。 | 注意缓存策略，避免玩家加载旧资源。 |

## 二、核心设计原则表

| 原则 | 含义 | 对我们的启发 |
| --- | --- | --- |
| 有意义决策 | 玩家每回合都应该面对“选 A 就放弃 B”的判断。 | 不要只给玩家很多按钮，要给真正有代价的选择。 |
| 信息透明 | 玩家要能知道规则、收益、代价和失败原因。 | 需要清楚的提示、面板、百科、Tooltip 和回合日志。 |
| 系统联动 | 地图、城市、资源、科技、外交、战争要互相影响。 | 避免做一堆互不相关的小系统。 |
| 多路线竞争 | 科技、文化、外交、军事、经济都应能形成胜利压力。 | 每条路线都要有明确目标、资源需求和反制方式。 |
| 重开价值 | 随机地图、不同文明、不同邻居能让每局不一样。 | 早期探索和地图生成很重要。 |
| 控制复杂度 | 复杂不等于堆内容，太多单位/建筑会压垮玩家。 | 第一版要少而清楚，先验证循环。 |
| 后期减负 | 大帝国后期容易变成重复维护。 | 要考虑队列、自动化、区域化或阶段结算。 |
| 工程可验证 | 每个系统都要能被日志、调试面板或测试地图验证。 | 原型不是只看能不能跑，还要看能不能调。 |
| 性能优先级 | 地图拖拽、缩放、单位显示、AI 结算不能明显卡顿。 | 第一版就要有 FPS 和对象数量指标。 |
| Web 可访问性 | 复杂面板用 DOM 可以更容易处理文本、表格、键盘和响应式。 | 地图用 WebGL，复杂 UI 用 DOM。 |

## 三、需要回答的问题表

| 分类 | 问题 | 为什么重要 | 推荐决策 |
| --- | --- | --- | --- |
| 游戏定位 | 我们想做多重度？ | 决定系统规模、UI 复杂度和开发周期。 | 先做中轻度原型，再决定是否加深。 |
| 游戏定位 | 一局理想时长是多少？ | 文明类游戏最容易失控成超长局。 | 第一版以 30 回合、20-40 分钟为目标。 |
| 游戏定位 | 平台是什么？ | 平台会影响操作方式、地图尺寸和 UI 密度。 | 桌面浏览器 Web Demo 优先。 |
| 游戏定位 | 玩家是谁？ | 硬核玩家和休闲玩家对复杂度接受度不同。 | 先定义为喜欢策略但不想读厚手册的玩家。 |
| 游戏定位 | 主题是什么？ | 主题决定资源、科技、文明和美术方向。 | 先在真实历史、架空文明、东方王朝中选一个；原型可用中性占位主题。 |
| 核心循环 | 玩家每回合最主要做哪三件事？ | 决定游戏的基本手感。 | 探索/建设、选择研究、处理竞争。 |
| 核心循环 | 前 10 回合如何好玩？ | 早期体验决定玩家是否继续。 | 开局要有探索发现、城市选址和第一项科技选择。 |
| 核心循环 | 中期如何制造路线分化？ | 防止所有玩家走同一套路。 | 用资源分布、邻居压力和科技分支制造差异。 |
| 核心循环 | 后期如何避免拖沓？ | 4X 常见问题是后期无聊但还没结束。 | 设计胜利赛跑、事件压力、管理自动化。 |
| 核心循环 | 落后玩家有没有翻盘路径？ | 防止滚雪球过早决定胜负。 | 加入联盟、危机、奇观、科技追赶或外交制衡。 |
| 教学体验 | 第一版是否需要新手引导？ | 系统多，没有引导会让玩家不知道先点什么。 | 必须做前 5 分钟引导，覆盖移动、研究、生产、结束回合。 |
| 操作手感 | 是否需要相机拖拽、缩放、路径预览？ | 地图操作是体验核心。 | 第一版必须支持拖拽、滚轮缩放、选中高亮，路径预览作为建议项。 |
| 调试地图 | 是否需要固定地图和地图编辑能力？ | 随机地图难以复现 bug。 | 第一版提供固定调试地图和地图种子，编辑器第二版再做。 |
| 事件系统 | 是否加入随机/时代事件？ | 后期容易重复，需要变化来源。 | 第一版只预留事件系统结构，先做少量测试事件。 |
| 经济数值 | 每回合如何计算资源和增长？ | 数值模型是平衡核心。 | 第一版写清回合结算顺序，并提供结算日志。 |
| 地图扩张 | 地图尺寸多大？ | 影响探索节奏和冲突密度。 | 12x12 到 20x20。 |
| 地图扩张 | 是否随机生成？ | 影响重玩价值。 | 随机资源和地形，但保留固定测试地图。 |
| 地图扩张 | 地图是方格、六边形，还是伪 3D？ | 影响坐标系统、寻路、点击命中和美术。 | 原型建议方格更快；如果强调文明感，可用六边形。 |
| 地图扩张 | 城市选址为什么重要？ | 如果哪里建城都一样，地图就失去意义。 | 河流、资源、丘陵、海岸影响产出和防御。 |
| 地图扩张 | 扩张的代价是什么？ | 防止无限铺城成为唯一策略。 | 维护费、满意度、距离成本或政策限制。 |
| 经济资源 | 基础资源有哪些？ | 决定游戏数学模型。 | 第一版只保留粮食、生产力、金币、科技。 |
| 经济资源 | 哪些资源是局部，哪些是全局？ | 影响城市管理和战略争夺。 | 粮食/生产力偏城市局部，金币/科技偏全局。 |
| 经济资源 | 贸易是否重要？ | 决定经济路线和地理连接的价值。 | 第一版只做被动经济加成；主动贸易路线和外交交易后续扩展。 |
| 经济资源 | 资源短缺会造成什么问题？ | 稀缺性是冲突来源。 | 战略资源限制高级单位生产。 |
| 科技文化 | 科技树有多少层？ | 影响学习成本和长期规划。 | 原型先做 8-12 个科技。 |
| 科技文化 | 科技是否绑定时代？ | 决定游戏阶段感。 | 第一版可先不做时代，只做早中期科技。 |
| 科技文化 | 玩家能否跳科技？ | 影响路线自由度和平衡。 | 允许少量分支，但保留关键前置。 |
| 科技文化 | 文化/制度是否与科技分开？ | 分开会增加深度，也增加复杂度。 | 原型先不分，第二版再加制度。 |
| 文明差异 | 文明差异来自哪里？ | 决定重开价值和阵营特色。 | 先用 2-3 个简单特性，不急着做大量文明。 |
| 文明差异 | 是否允许领袖和文明分离？ | 会增加组合空间，也增加平衡成本。 | 先记录为可选设计，不放进第一版。 |
| 外交战争 | 外交是轻量还是核心玩法？ | 影响 AI 和 UI 工作量。 | 原型先做关系值、紧张状态、宣战和原因解释，不做交易。 |
| 外交战争 | AI 会记仇吗？ | 决定外交是否可信。 | 至少记录宣战、抢地、边境压力等行为。 |
| 外交战争 | 宣战有什么代价？ | 防止战争成为无脑最优解。 | 加入金币成本、关系惩罚或厌战。 |
| 外交战争 | 非军事路线如何对抗军事路线？ | 保证多路线可行。 | 防御建筑、联盟、经济制裁或胜利竞速。 |
| 胜利条件 | 有几种胜利？ | 决定玩家路线数量。 | 原型只做征服胜利和科技胜利。 |
| 胜利条件 | 每种胜利对应什么核心行为？ | 防止胜利条件空洞。 | 征服靠占首都，科技靠完成终极项目。 |
| 胜利条件 | 玩家能否看见对手进度？ | 可见压力能提升紧张感。 | 胜利进度必须公开或半公开。 |
| 胜利条件 | 回合上限如何结算？ | 避免游戏无尽拖延。 | 原型 30 回合按分数复盘。 |
| Web 平台 | 第一版是桌面 Web 还是移动 Web？ | 影响 UI 密度、输入方式和性能目标。 | 先做桌面 Web，移动端第二阶段适配。 |
| Web 平台 | 是否需要离线可玩？ | 影响资源缓存、存档和部署方式。 | 原型先不要求完整离线，但要能本地存档。 |
| 渲染 | 地图用 Canvas 2D、WebGL 还是 WebGPU？ | 决定性能上限和开发复杂度。 | 第一版用 WebGL2，WebGPU 预留。 |
| 渲染 | UI 是画在 WebGL 里还是 DOM 里？ | 决定科技树、城市面板、Tooltip 的开发效率。 | 地图 WebGL，复杂 UI 用 DOM。 |
| 渲染 | 是否使用渲染库？ | 影响底层工作量和后续扩展。 | 推荐 TypeScript + Vite + PixiJS/WebGL + React DOM UI。 |
| 性能 | 第一版性能目标是多少？ | 没有指标就无法判断是否需要优化。 | 桌面端 60 FPS，低端设备至少 30 FPS。 |
| 性能 | AI 和寻路是否会阻塞页面？ | Web 主线程被阻塞会导致页面卡死。 | AI、寻路、地图生成预留 Web Worker。 |
| 存档 | 存档保存哪些内容？ | 影响 GameState 数据结构。 | 地图种子、回合数、玩家状态、AI 状态、城市、单位、科技、外交。 |
| 部署 | 是否需要一键发链接试玩？ | Web 原型的最大优势是快速收集反馈。 | 静态站点部署即可。 |
| 资源 | 地形、单位、建筑图是否用图集？ | 影响 WebGL 性能和加载速度。 | 第一版就用 texture atlas 思路。 |
| 输入 | 是否支持快捷键？ | 策略游戏操作很多，快捷键能减少疲劳。 | 至少支持结束回合、打开科技、选中下一个单位。 |
| 调试 | 是否需要开发者调试面板？ | 策略游戏系统多，没调试面板会很难查问题。 | 第一版必须有。 |
| 原型范围 | 第一版是否只做单人？ | 多人会显著增加复杂度。 | 第一版只做单人。 |
| 原型范围 | 第一版需要几个 AI？ | AI 数量影响调试难度。 | 先做 1 个 AI，稳定后加到 2 个。 |
| 原型范围 | 第一版做几个单位？ | 单位太多会增加平衡成本。 | 侦察兵、战士、建造者、弓手即可。 |
| 成功标准 | 玩家 30 回合后是否想再开一局？ | 这是原型最重要的判断。 | 试玩后重点问“想不想重开”。 |
| 成功标准 | 玩家是否知道自己为什么输？ | 决定信息透明度是否够。 | 结束时给出复盘面板。 |
| 成功标准 | 玩家是否在至少两条路线之间纠结？ | 说明策略选择成立。 | 保证科技、扩张、军事之间有资源冲突。 |

## 四、Web 玩法原型范围表

| 内容 | 建议范围 | 原因 |
| --- | --- | --- |
| 平台 | 桌面浏览器优先 | 文明类 UI 密度高，先不要被移动端限制。 |
| 技术栈 | TypeScript + Vite + PixiJS/WebGL + React DOM UI | 便于快速开发、组件化 UI、地图性能和后期维护。 |
| 渲染方案 | WebGL2 优先，Canvas 2D 可作为极简 fallback | 地图缩放、战争迷雾、单位批量渲染更适合 WebGL。 |
| UI 方案 | 城市面板、科技树、外交面板、回合提示用 DOM/前端框架 | 表格、按钮、Tooltip 用 DOM 更快更清楚。 |
| WebGPU | 不进第一版核心，渲染层预留接口 | WebGPU 是未来方向，但第一版要先稳定跑通。 |
| 性能目标 | 桌面端 60 FPS，低端设备至少 30 FPS | 策略游戏不需要动作游戏级响应，但拖拽缩放不能卡。 |
| 地图 | 12x12 到 20x20，方格或六边形，支持缩放和平移 | 足够产生探索和冲突，也能验证 WebGL 地图操作。 |
| 玩家数量 | 1 名玩家 + 1 个 AI | 降低 AI 和外交复杂度。 |
| 城市数量 | 每方最多 3 座城市 | 控制管理压力。 |
| 基础资源 | 粮食、生产力、金币、科技 | 覆盖成长、建造、经济和研究。 |
| 地形 | 平原、森林、丘陵、河流、山脉、水域 | 足够让选址和移动产生差异。 |
| 单位 | 侦察兵、战士、建造者、弓手 | 覆盖探索、近战、建设、远程。 |
| 科技 | 8-12 个 | 足够形成路线，但不会失控。 |
| 建筑 | 粮仓、工坊、市场、学院、城墙 | 对应人口、生产、经济、科技、防御。 |
| 胜利 | 征服胜利 + 科技胜利 | 一个军事路线，一个非军事路线。 |
| 局长 | 30 回合 | 快速验证核心循环。 |
| 存档 | 至少支持本地保存一局 | 方便测试和玩家中断后继续。 |
| 输入 | 鼠标点击、拖拽、滚轮缩放、快捷键结束回合 | Web 桌面版的基础操作。 |
| 调试面板 | 显示 FPS、当前回合、选中单位、AI 状态、资源结算 | 方便开发阶段定位问题。 |
| 部署 | 可静态部署，发链接即可试玩 | Web 原型的优势就是快速试玩和反馈。 |

## 六、Web 方向与 WebGL 技术落地表

| 模块 | 主要内容 | 设计意义 | 需要重点注意 |
| --- | --- | --- | --- |
| Web 平台定位 | 明确第一版是桌面浏览器 Web Demo，未来可再考虑桌面封装或移动端。 | 决定技术栈、性能目标、UI 密度和部署方式。 | 第一版建议先做桌面浏览器，移动端只做兼容预留。 |
| WebGL 渲染系统 | 用 WebGL 渲染地图、地形、单位、资源、战争迷雾、路径预览、动画。 | 保证大地图缩放、拖拽、批量单位显示时仍然流畅。 | 不要把复杂 UI 全塞进 WebGL，UI 面板建议用 DOM。 |
| WebGPU 预留 | 在渲染层做抽象，未来可从 WebGL 切到 WebGPU 或支持双后端。 | WebGPU 更适合现代 GPU、复杂渲染和计算任务。 | 第一版不要强依赖 WebGPU，WebGL 更稳。 |
| Canvas/WebGL/DOM 分层 | 地图画面走 WebGL，复杂面板、科技树、城市详情、外交界面走 DOM。 | 降低 UI 开发难度，同时保留地图性能。 | 需要处理坐标换算、缩放、点击命中和层级遮挡。 |
| 前端技术栈 | TypeScript + Vite + PixiJS/WebGL + React DOM UI。 | 提高开发效率，方便组件化 UI 和数据驱动。 | 游戏状态不要完全绑死在 UI 框架里。 |
| 渲染库选择 | 2D/2.5D 优先 PixiJS；Phaser 可作为完整游戏框架备选；真 3D 再考虑 Three.js/Babylon.js。 | 避免从零写所有 WebGL 底层代码。 | 策略游戏 UI 很重，别选只适合动作游戏的架构。 |
| 游戏状态架构 | 地图、城市、单位、科技、外交、胜利进度统一放在 GameState。 | 方便回合结算、存档、AI 读取和复盘。 | 渲染层只读状态，不让渲染对象直接改规则。 |
| 回合模拟系统 | 每回合按固定顺序处理：玩家输入、AI 决策、城市生产、资源结算、胜利检测。 | 保证规则可预测、可调试、可存档。 | 回合结算顺序要写清楚，否则 bug 很难查。 |
| Web Worker | 把 AI、寻路、地图生成、胜利评估等耗时任务放到 Worker。 | 防止 AI 思考时页面卡顿。 | Worker 与主线程通信需要序列化数据，GameState 结构要轻。 |
| 存档系统 | 使用 IndexedDB 保存地图种子、回合数、城市、单位、科技和外交状态。 | 玩家可以中途退出，也方便测试回放。 | LocalStorage 只适合小配置，复杂存档更适合 IndexedDB。 |
| 资源加载 | 地形图集、单位图集、UI 图标、音频、配置表、字体。 | 控制首屏加载时间，避免游戏中卡顿。 | 地图贴图建议用 texture atlas，减少频繁切图。 |
| 性能预算 | 设定 FPS、最大地图格子、最大单位、最大城市、首屏加载时间。 | 防止原型越做越卡。 | 第一版就要有性能面板，显示 FPS、单位数、渲染对象数。 |
| 输入系统 | 鼠标点击、拖拽地图、滚轮缩放、右键移动、触控缩放。 | Web 游戏必须适配浏览器常见交互。 | 浏览器默认滚动、右键菜单、触控手势需要处理。 |
| 响应式布局 | 适配 16:9、笔记本、小屏，移动端第二阶段再深做。 | 决定 UI 是否能在网页中自然使用。 | 文明类 UI 密度高，移动端第一版不建议强做。 |
| 部署发布 | 静态站点部署、版本号、资源缓存、错误日志、性能数据收集。 | 方便快速发给别人试玩。 | 缓存策略要注意，否则玩家可能加载旧版本资源。 |
| 调试工具 | 地图调试层、单位坐标显示、资源产出显示、AI 意图显示、回合日志。 | 策略游戏 bug 多，没有调试工具会很慢。 | AI 决策必须能解释，否则很难判断是设计问题还是 bug。 |
