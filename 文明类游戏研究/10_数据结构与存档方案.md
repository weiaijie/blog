# 10 数据结构与存档方案

本文档定义第一版 Web 文明类原型的数据结构、存档、读档、迁移、回放和调试导出方案。它承接 `07_Web游戏引擎选型调研.md`、`08_工程架构设计.md`、`09_玩法规则规格表.md` 的结论：**PixiJS 只负责渲染，React 只负责 UI，规则状态统一放在纯数据 `GameState`，存档只保存可序列化数据。**

本文档是 `GameState`、`SaveGame`、`CommandRecord` 的权威 schema 来源。其他文档如果出现同名结构，只作为摘要说明；实现时以本文为准。

第一版目标不是做完整云存档或多人同步，而是保证 30 回合原型具备三个能力：

| 能力 | 第一版要求 |
| --- | --- |
| 可继续 | 刷新页面或关闭浏览器后，能从 IndexedDB 读取最近自动存档或手动存档继续。 |
| 可复现 | 固定 seed、固定 `GameState`、固定 `CommandLog` 能复现主要 bug。 |
| 可迁移 | 后续字段变化时，旧存档能通过 `schemaVersion` 迁移或给出明确错误。 |

## 一、设计原则

| 原则 | 决策 | 原因 |
| --- | --- | --- |
| 纯数据状态 | `GameState` 只保存 JSON/structured clone 可处理的数据。 | 避免 PixiJS、React、Worker 对象污染存档。 |
| 规则状态唯一 | `GameState` 是唯一规则数据源。 | 存档、回放、AI、测试都依赖同一份状态。 |
| 实体 ID 稳定 | 城市、单位、玩家、地块全部使用稳定 ID。 | 方便 diff、日志、回放、存档迁移。 |
| 规则变化走 RuleCommand | 玩家、AI、系统自动动作只要改变规则状态，都进入 `CommandLog`。UIIntent 和普通 DebugCommand 不进入 replay 日志。 | 支持复现和规则审计，同时避免选中、hover、相机等 UI 状态污染回放。 |
| EventLog 不当状态源 | `EventLog` 记录结果和解释，不用于还原状态。 | 避免日志缺失导致读档错误。 |
| 存档带版本 | `SaveGame` 和 `GameState` 都保存 `schemaVersion`。 | 字段变化时可迁移。 |
| 小而完整 | 第一版保存完整快照，Command replay 作为调试增强。 | 快速稳定，避免早期就被完整录像系统拖慢。 |
| 数据最小化 | 不保存 Sprite、Texture、DOM、临时 hover、动画状态。 | 降低存档体积和版本耦合。 |

## 二、GameState 顶层结构表

第一版推荐当前结构版本：

| 项目 | 值 |
| --- | --- |
| `CURRENT_SCHEMA_VERSION` | `1` |
| `SAVE_DB_NAME` | `civlike-web-prototype` |
| `SAVE_DB_VERSION` | `1` |
| 存档格式 | IndexedDB object store + JSON 结构化数据 |
| 压缩 | 第一版不压缩，Debug Export 可直接阅读 |

```ts
type GameState = {
  schemaVersion: number;
  gameId: GameId;
  createdAt: number;
  updatedAt: number;
  buildVersion: string;
  rulesVersion: string;

  seed: string;
  rngState: RngState;
  turn: number;
  phase: TurnPhase;
  activePlayerId: PlayerId;

  settings: GameRulesSettings;
  map: MapState;
  players: Record<PlayerId, PlayerState>;
  cities: Record<CityId, CityState>;
  units: Record<UnitId, UnitState>;
  tech: TechState;
  diplomacy: DiplomacyState;
  victory: VictoryState;

  commandLog: CommandRecord[];
  eventLog: GameEvent[];
  stats: GameStats;
};
```

| 字段 | 类型 | 是否进存档 | 说明 |
| --- | --- | --- | --- |
| `schemaVersion` | number | 是 | 数据结构版本，用于迁移。 |
| `gameId` | string | 是 | 单局唯一 ID。 |
| `createdAt` / `updatedAt` | number | 是 | 调试和存档排序使用，不参与规则结算。 |
| `buildVersion` | string | 是 | 应用构建版本，定位 bug。 |
| `rulesVersion` | string | 是 | 规则配置版本，后续数值变化可追踪。 |
| `seed` | string | 是 | 地图、AI、随机事件的初始种子。 |
| `rngState` | object | 是 | 当前随机数生成器状态。 |
| `turn` | number | 是 | 当前回合。第一版 1-30。 |
| `phase` | enum | 是 | 当前阶段，例如玩家行动、AI 计划、结算。 |
| `activePlayerId` | string | 是 | 当前行动方。 |
| `settings` | object | 是 | 本局规则设置，例如地图尺寸、回合上限。 |
| `map` | `MapState` | 是 | 地图逻辑数据。 |
| `players` | Record | 是 | 玩家和 AI 的全局状态。 |
| `cities` | Record | 是 | 城市实体状态。 |
| `units` | Record | 是 | 单位实体状态。 |
| `tech` | `TechState` | 是 | 科技树进度。 |
| `diplomacy` | `DiplomacyState` | 是 | 外交和战争状态。 |
| `victory` | `VictoryState` | 是 | 胜利进度和最终结果。 |
| `commandLog` | array | 是 | 成功执行的命令，用于回放和调试。 |
| `eventLog` | array | 是，限量 | 展示和调试日志，第一版保存最近 300 条。 |
| `stats` | object | 是 | 复盘和调试指标。 |

## 三、实体 ID 规范

实体 ID 必须稳定、可读、可排序。第一版不需要复杂分布式 ID，推荐使用带前缀的自增序号。

| 实体 | ID 示例 | 生成规则 | 排序规则 |
| --- | --- | --- | --- |
| 游戏 | `game_20260522_001` | 创建新局时生成。 | 按 `createdAt`。 |
| 玩家 | `player_human`, `player_ai_1` | 固定 ID。 | 人类玩家优先，AI 按编号。 |
| 地块 | `tile_04_09` | 方格地图用 `x/y` 派生。 | `y` 后 `x`。 |
| 城市 | `city_player_human_001` | 玩家 ID + 自增序号。 | 创建顺序。 |
| 单位 | `unit_player_human_001` | 玩家 ID + 自增序号。 | 创建顺序。 |
| 科技 | `tech_archery` | 配置表固定 ID。 | 科技树配置顺序。 |
| 建筑 | `building_granary` | 配置表固定 ID。 | 配置表顺序。 |
| 命令 | `cmd_000001` | 当前局自增序号。 | 自增序号。 |
| 事件 | `evt_000001` | 当前局自增序号。 | 自增序号。 |
| 存档 | `autosave_latest`, `manual_001` | 固定槽位或用户槽位。 | 保存时间。 |

| 约束 | 决策 |
| --- | --- |
| 不使用数组下标当实体身份 | 数组顺序可能变化，迁移和删除后容易错位。 |
| `Record<Id, Entity>` 优先 | 查询、diff、引用更稳定。 |
| 实体内保存自己的 `id` | 便于 Debug Export 单独查看实体。 |
| 引用必须使用 ID | 城市引用地块、单位引用地块、事件引用实体都使用 ID。 |
| 删除实体不复用 ID | 死亡单位、被移除城市的 ID 不再分配给新实体。 |

## 四、实体表

### 1. 玩家实体

```ts
type PlayerState = {
  id: PlayerId;
  kind: "human" | "ai";
  name: string;
  color: string;
  capitalCityId?: CityId;
  cityIds: CityId[];
  unitIds: UnitId[];
  resources: GlobalResources;
  research: PlayerResearchState;
  ai?: AiPublicState;
  defeated: boolean;
};
```

| 字段 | 说明 | 第一版规则来源 |
| --- | --- | --- |
| `resources.gold` | 全局金币库存。 | 城市金币收入 - 维护费。 |
| `resources.scienceOverflow` | 科技溢出或小数累计。 | 人口科技加成可能产生小数。 |
| `research.currentTechId` | 当前研究科技。 | 每方同时只研究 1 项。 |
| `research.progressByTechId` | 每项科技累计进度。 | 切换科技时进度保留。 |
| `ai.intent` | AI 当前意图。 | 调试面板展示 AI 目标。 |
| `defeated` | 是否失败。 | 首都被占领或所有城市丢失。 |

### 2. 地图与地块实体

```ts
type MapState = {
  kind: "square";
  width: number;
  height: number;
  tiles: Record<TileId, TileState>;
  startingPositions: Record<PlayerId, TileId>;
  debugSeedName?: string;
};

type TileState = {
  id: TileId;
  coord: { kind: "square"; x: number; y: number };
  terrain: TerrainType;
  feature?: FeatureType;
  resource?: ResourceType;
  ownerId?: PlayerId;
  cityId?: CityId;
  unitIds: UnitId[];
  exploredBy: PlayerId[];
  visibleBy: PlayerId[];
  yields: TileYield;
};
```

| 字段 | 说明 | 存档注意 |
| --- | --- | --- |
| `kind` | 第一版固定为 `square`。 | 保留字段，后续迁移到 hex 时使用。 |
| `tiles` | 地块全集。 | 使用 `Record`，不要保存渲染坐标。 |
| `unitIds` | 当前地块上的单位。 | 与 `UnitState.tileId` 需要一致性校验。 |
| `exploredBy` / `visibleBy` | 战争迷雾状态。 | 保存玩家 ID 数组，读档后重新渲染。 |
| `yields` | 地块基础产出。 | 可由地形派生，但第一版直接保存便于调试。 |

### 3. 城市实体

```ts
type CityState = {
  id: CityId;
  ownerId: PlayerId;
  name: string;
  tileId: TileId;
  foundedTurn: number;

  population: number;
  hp: number;
  maxHp: number;
  defense: number;

  foodStored: number;
  productionStored: number;
  productionQueue: ProductionOrder[];
  buildingIds: BuildingId[];
  workedTileIds: TileId[];
  yieldsLastTurn: CityYieldSummary;
};
```

| 字段 | 说明 | 第一版规则来源 |
| --- | --- | --- |
| `population` | 城市人口。 | 初始 1，按粮食成长。 |
| `foodStored` | 粮食库存。 | 达到阈值人口 +1。 |
| `productionStored` | 当前生产项目累计生产力。 | 项目完成后保留溢出。 |
| `productionQueue` | 当前和后续生产项。 | 第一版至少 1 个当前项。 |
| `buildingIds` | 已建建筑。 | 粮仓、工坊、市场、学院、城墙。 |
| `workedTileIds` | 自动工作的地块。 | 数量等于人口。 |
| `yieldsLastTurn` | 上回合产出摘要。 | 用于 UI 和 EventLog 校验。 |

### 4. 单位实体

```ts
type UnitState = {
  id: UnitId;
  ownerId: PlayerId;
  type: UnitType;
  tileId: TileId;
  createdTurn: number;

  hp: number;
  maxHp: number;
  attack: number;
  range: number;
  movement: number;
  movementLeft: number;
  vision: number;
  maintenanceGold: number;

  hasAttackedThisTurn: boolean;
  status: "active" | "fortified" | "dead";
};
```

| 字段 | 说明 | 存档注意 |
| --- | --- | --- |
| `tileId` | 单位逻辑位置。 | 读档后 PixiJS Sprite 从该字段重建。 |
| `movementLeft` | 当前剩余行动力。 | 回合开始恢复。 |
| `hasAttackedThisTurn` | 攻击后不能再移动或攻击。 | 回合开始清理。 |
| `status` | 单位状态。 | 死亡单位可从 `units` 删除，也可短期标记 `dead` 后清理。 |

### 5. 科技、外交、胜利

| 状态 | 推荐结构 | 第一版内容 |
| --- | --- | --- |
| `TechState` | `completedByPlayerId`、`progressByPlayerId`、`currentByPlayerId` | 12 项以内科技，支持切换保留进度。 |
| `DiplomacyState` | `relations: Record<PairId, RelationState>` | 第一版包含 `unknown`、`peace`、`tense`、`war`、关系值、最近原因、宣战冷却；不包含交易、同盟、议和。 |
| `VictoryState` | `status`、`winnerId`、`type`、`progressByPlayerId`、`scorePreview` | 征服、科技、30 回合分数胜利。 |
| `GameStats` | `turnsPlayed`、`commandsExecuted`、`unitsKilled`、`citiesFounded`、`techsCompleted` | 复盘和调试用。 |

## 五、SaveGame 结构

`SaveGame` 是写入 IndexedDB 的顶层对象。它包含元数据、预览信息、完整状态和可选校验摘要。

```ts
type SaveGame = {
  saveId: SaveId;
  slotKind: "autosave" | "manual" | "debug";
  schemaVersion: number;
  buildVersion: string;
  rulesVersion: string;
  savedAt: number;
  label: string;

  preview: SavePreview;
  state: GameState;
  integrity: SaveIntegrity;
};

type SavePreview = {
  gameId: GameId;
  turn: number;
  phase: TurnPhase;
  playerName: string;
  mapSize: string;
  victoryStatus: string;
  scorePreview: Record<PlayerId, number>;
  thumbnailDataUrl?: string;
};

type SaveIntegrity = {
  stateHash: string;
  commandCount: number;
  eventCount: number;
  createdBy: "autosave" | "manual" | "debug-export";
};
```

| 字段 | 说明 |
| --- | --- |
| `saveId` | 存档槽位 ID，例如 `autosave_latest`、`manual_001`。 |
| `slotKind` | 区分自动、手动、调试存档。 |
| `label` | UI 展示名，例如“第 12 回合 - 科技领先”。 |
| `preview` | 存档列表无需加载完整状态即可展示的信息。 |
| `state` | 完整 `GameState` 快照。 |
| `integrity.stateHash` | 对关键状态生成摘要，读档和回放测试使用。 |
| `thumbnailDataUrl` | 可选缩略图。第一版可不做，避免存档膨胀。 |

## 六、IndexedDB Stores

第一版使用 IndexedDB 保存结构化存档，LocalStorage 只保存轻量用户偏好。

| Store | keyPath | 主要内容 | 索引 | 第一版要求 |
| --- | --- | --- | --- | --- |
| `saves` | `saveId` | `SaveGame` 完整存档。 | `gameId`、`slotKind`、`savedAt` | 必须。 |
| `savePreviews` | `saveId` | 轻量预览信息。 | `savedAt`、`slotKind` | 建议。若实现复杂，可从 `saves` 派生。 |
| `settings` | `key` | 音量、调试开关、最后打开槽位。 | 无 | 必须。 |
| `debugExports` | `exportId` | 本地调试包历史。 | `createdAt`、`gameId` | 可选。 |
| `migrationLog` | `id` | 迁移记录和失败原因。 | `createdAt` | 建议。 |

### Store 设计说明

| 主题 | 决策 |
| --- | --- |
| 自动存档槽位 | 第一版只保留 `autosave_latest`，第二版可加滚动槽 `autosave_turn_10`。 |
| 手动存档槽位 | 第一版至少 `manual_001`，可扩展到 3-5 个槽。 |
| 预览信息 | 存档列表优先读 `savePreviews`，避免加载完整大对象。 |
| 设置保存 | `settings` 保存 UI 偏好，不进入 `GameState`。 |
| 调试导出 | Debug Export 主要下载 JSON 文件；本地 store 只作为可选历史。 |

### LocalStorage 只保存这些内容

| key | 内容 |
| --- | --- |
| `civlike.lastSaveId` | 上次加载的存档槽位。 |
| `civlike.uiSettings` | 音量、调试面板开关、是否显示坐标层。 |
| `civlike.acceptedSchemaWarning` | 用户是否确认过旧存档警告。 |

不要把完整 `GameState` 写进 LocalStorage。它容量小、同步阻塞主线程，也不适合较大结构化数据。

## 七、存档流程

### 1. 自动存档流程

自动存档触发点：玩家成功执行 `END_TURN` 并完成本回合结算后。

```text
END_TURN Command 成功
  -> Simulation 完成玩家、AI、世界结算
  -> GameStateStore 得到新状态
  -> trimEventLog 保留最近 300 条展示事件
  -> buildSavePreview
  -> computeStateHash
  -> StorageService.save("autosave_latest")
  -> EventLog 写入 SAVE_COMPLETED 或 SAVE_FAILED
```

| 步骤 | 要求 |
| --- | --- |
| 触发时机 | 回合结算完成后，不在结算中途保存半状态。 |
| UI 表现 | 保存中不阻塞地图拖拽和日志查看。 |
| 失败处理 | IndexedDB 写入失败时写 `SAVE_FAILED` 事件，并提示玩家可手动导出 Debug JSON。 |
| 覆盖策略 | `autosave_latest` 直接覆盖旧自动存档。 |
| 性能目标 | 20x20 地图、20 个单位以内，自动存档不造成明显卡顿。 |

### 2. 手动存档流程

手动存档由玩家从菜单或快捷键触发。

```text
玩家点击保存
  -> CommandFactory 创建 SAVE_GAME
  -> Validator 检查当前 phase 是否允许保存
  -> StorageService.save("manual_001")
  -> 更新 savePreviews
  -> UI 显示保存结果
```

| 项目 | 决策 |
| --- | --- |
| 第一版槽位 | 至少 1 个手动槽 `manual_001`。 |
| 允许保存阶段 | `PLAYER_ACTION`、`PLAYER_END` 后稳定阶段、胜利复盘阶段。 |
| 不建议保存阶段 | `AI_PLAN` 等 Worker 请求进行中，除非先取消或等待完成。 |
| 覆盖提示 | 覆盖手动槽位前提示。 |
| 标签 | 默认使用“第 N 回合 - 玩家名”，允许后续加自定义名称。 |

### 3. 存档前校验

| 校验项 | 失败处理 |
| --- | --- |
| `GameState.schemaVersion === CURRENT_SCHEMA_VERSION` | 阻止保存并提示开发错误。 |
| `gameId`、`seed`、`turn`、`map` 存在 | 阻止保存，导出 Debug 包。 |
| 所有城市 owner 存在 | 阻止保存，记录 `SAVE_VALIDATION_FAILED`。 |
| 所有单位 tile 存在 | 阻止保存，记录异常单位 ID。 |
| 地块 `unitIds` 与 `units.tileId` 一致 | 尝试生成诊断，不自动修复规则状态。 |
| `commandLog` 命令序号连续 | 允许保存但记录 warning，供 replay 测试处理。 |

## 八、读档流程

```text
玩家选择存档
  -> StorageService.load(saveId)
  -> validateSaveEnvelope
  -> migrateSaveGame
  -> validateGameState
  -> cancelPendingWorkerRequests
  -> GameStateStore.replaceState
  -> UIStateStore.resetForLoadedGame
  -> RenderEngine.rebuildFromState
  -> EventLog 写入 LOAD_COMPLETED
```

| 步骤 | 要求 |
| --- | --- |
| 读取 envelope | 先检查 `saveId`、`schemaVersion`、`state` 是否存在。 |
| 迁移 | 旧版本必须先迁移到当前版本，再进入游戏。 |
| 校验 | 校验实体引用、地图尺寸、当前玩家、回合阶段。 |
| Worker | 读档前取消或忽略旧 `requestId`，避免旧 AI 响应污染新状态。 |
| UIState | 清空选中、hover、打开面板，保留相机可选重置到首都。 |
| RenderEngine | 销毁或回收旧 Sprite，从新 `GameState` 重建。 |
| 错误展示 | 明确告诉玩家：版本不兼容、存档损坏、浏览器存储不可用。 |

### 读档后重建内容

| 内容 | 从哪里重建 | 是否存档 |
| --- | --- | --- |
| PixiJS Tile Sprite | `map.tiles` + 资源图集 | 否 |
| PixiJS Unit Sprite | `units` | 否 |
| 战争迷雾 overlay | `tiles.visibleBy/exploredBy` | 否 |
| 城市面板 | `cities` + selectors | 否 |
| 科技树 UI | `tech` + 配置表 | 否 |
| Tooltip/hover | 用户重新操作 | 否 |
| Camera | `UIState` 或默认首都位置 | 可选设置，不进 `GameState` |

## 九、版本迁移

### 1. 版本字段

| 字段 | 所在位置 | 用途 |
| --- | --- | --- |
| `SaveGame.schemaVersion` | 存档 envelope | 判断存档外层结构。 |
| `GameState.schemaVersion` | 状态主体 | 判断规则状态结构。 |
| `buildVersion` | 两者都有 | 定位由哪个应用版本保存。 |
| `rulesVersion` | 两者都有 | 定位数值配置版本。 |

### 2. 迁移接口

```ts
type Migration = {
  from: number;
  to: number;
  description: string;
  run: (save: unknown) => SaveGame;
};

function migrateSaveGame(input: unknown): SaveGame {
  let save = validateEnvelopeShape(input);
  while (save.schemaVersion < CURRENT_SCHEMA_VERSION) {
    const migration = migrations.find((item) => item.from === save.schemaVersion);
    if (!migration) throw new SaveMigrationError(save.schemaVersion);
    save = migration.run(save);
  }
  return save;
}
```

### 3. 第一版迁移策略

| 情况 | 处理 |
| --- | --- |
| `schemaVersion === 1` | 直接校验后加载。 |
| `schemaVersion < 1` | 不支持，提示存档过旧。 |
| `schemaVersion > CURRENT_SCHEMA_VERSION` | 不加载，提示需要更新游戏版本。 |
| 缺少可补默认字段 | 迁移时补默认值，并写入 `migrationLog`。 |
| 缺少关键字段 | 迁移失败，允许导出原始存档供调试。 |

### 4. 未来迁移示例

| 变更 | 迁移方式 |
| --- | --- |
| 新增 `culture` 资源 | 给所有玩家和城市补 `culture: 0`。 |
| 方格切六边形 | 新建 `coord.kind = "hex"`，保存旧坐标到 `legacyCoord`，需要专门迁移地图。 |
| 科技 ID 重命名 | 使用映射表把旧 `tech_writing` 转为新 ID。 |
| 城市建筑效果拆分 | 根据旧 `buildingIds` 生成新 `modifiers`。 |
| 外交系统扩展 | 给所有玩家组合补默认关系状态。 |

## 十、Replay 与命令日志方案

第一版采用“完整快照 + 命令日志”的折中方案。玩家读档依赖快照，开发调试可用命令日志复现。

### 1. CommandRecord

```ts
type CommandRecord = {
  sequence: number;
  commandId: CommandId;
  turn: number;
  phase: TurnPhase;
  actorId: PlayerId | "system";
  source: "player" | "ai" | "tutorial" | "debug" | "system";
  type: RuleCommandType;
  payload: unknown;
  rngBefore: RngState;
  rngAfter: RngState;
  result: "applied" | "rejected";
  validationError?: ValidationErrorCode;
  stateHashAfter?: string;
  createdAt: number;
};
```

| 字段 | 作用 |
| --- | --- |
| `sequence` | 保证执行顺序稳定。 |
| `rngBefore` / `rngAfter` | 排查随机结果不一致。 |
| `result` | 第一版建议只把成功 Command 用于 replay，失败记录用于调试。 |
| `stateHashAfter` | Replay 测试时对比状态摘要。 |
| `source` | 区分玩家、AI、系统、教程、调试操作。 |

只有成功执行且改变规则状态的 `RuleCommand` 用于 replay。普通 UIIntent，例如选中单位、悬停地块、打开面板、相机移动，不写入 `CommandRecord`。开发模式下的 DebugCommand 如果会改变规则状态，必须显式标记 `source = "debug"`，并在 Replay 测试中可选择排除。

### 2. ReplayPackage

```ts
type ReplayPackage = {
  schemaVersion: number;
  replayVersion: number;
  gameId: GameId;
  initialSeed: string;
  initialSettings: GameRulesSettings;
  initialState?: GameState;
  commandLog: CommandRecord[];
  expectedFinalHash?: string;
};
```

| 阶段 | 方案 |
| --- | --- |
| 第一版 | Debug Export 内包含 `initialState`、当前 `GameState`、`CommandLog`、`EventLog`。 |
| 第一版测试 | 从导出的 `initialState` 开始重放后续命令，对比 `stateHashAfter`。 |
| 第二版 | 从 seed + 配置生成初始状态，再执行完整 `CommandLog`。 |
| 长期 | 支持 UI 级复盘时间轴、关键事件跳转、战斗回放。 |

### 3. Replay 确定性要求

| 风险 | 规避 |
| --- | --- |
| 遍历对象顺序不同 | Simulation 对玩家、城市、单位、地块 ID 显式排序。 |
| AI 输出不稳定 | AI 只读状态和 RNG，不读真实时间。 |
| Worker 返回乱序 | 主线程按 `requestId`、`turn`、`phase` 接受当前响应。 |
| 浮点误差 | 规则层尽量使用整数；小数科技收入使用固定精度。 |
| 渲染帧影响规则 | 动画和帧率不得驱动规则结算。 |
| 配置表变化 | Debug Export 带 `rulesVersion` 和关键配置摘要。 |

## 十一、EventLog 与日志保留

`EventLog` 用于解释结果，不作为还原状态的依据。

| 日志类型 | 是否进存档 | 保留策略 |
| --- | --- | --- |
| 玩家可见事件 | 是 | 最近 300 条。 |
| 调试事件 | 是，开发模式 | 最近 500 条或 Debug Export 全量导出。 |
| 高频 hover / path 事件 | 否 | 不记录。 |
| Worker 性能事件 | 是，摘要 | 记录请求类型、耗时、错误。 |
| 存档失败事件 | 是 | 必须记录。 |

```ts
type GameEvent = {
  id: EventId;
  turn: number;
  phase: TurnPhase;
  type: GameEventType;
  severity: "info" | "warning" | "error" | "debug";
  actorId?: PlayerId | "system";
  entityIds?: EntityId[];
  message: string;
  data?: Record<string, unknown>;
};
```

| 必须记录的事件 | 示例 |
| --- | --- |
| `SAVE_COMPLETED` | 自动存档完成。 |
| `SAVE_FAILED` | 浏览器存储不可用或配额不足。 |
| `LOAD_COMPLETED` | 成功读取第 12 回合存档。 |
| `LOAD_FAILED` | 存档版本高于当前版本。 |
| `MIGRATION_APPLIED` | 存档从 v1 迁移到 v2。 |
| `REPLAY_MISMATCH` | 第 18 条命令后状态摘要不一致。 |

## 十二、数据最小化

### 1. 不进入 GameState 的内容

| 内容 | 放在哪里 | 原因 |
| --- | --- | --- |
| PixiJS `Sprite`、`Texture`、`Container` | `RenderEngine` 内部缓存 | 无法稳定序列化，且与资源版本绑定。 |
| React 组件 local state | React 内部 | 展开折叠、输入框临时值不影响规则。 |
| hover/tooltip 状态 | `UIState` | 高频变化，不需要读档恢复。 |
| 相机动画状态 | `UIState` | 可重置或保存到 settings。 |
| Worker 运行中请求 | `WorkerClient` | 读档时取消重发。 |
| 音频播放位置 | Audio 系统 | 不影响规则。 |
| 性能采样明细 | Debug 工具 | 存摘要即可，明细只进 Debug Export。 |

### 2. 可以进入 Settings 的内容

| 内容 | 存储位置 |
| --- | --- |
| 音量 | LocalStorage 或 IndexedDB `settings`。 |
| 调试面板是否打开 | LocalStorage。 |
| 是否显示坐标层 | LocalStorage。 |
| 上次手动存档槽位 | LocalStorage。 |
| 首选语言 | LocalStorage 或应用配置。 |

### 3. 存档体积控制

| 项目 | 策略 |
| --- | --- |
| EventLog | 默认只保存最近 300 条，全量只在 Debug Export。 |
| CommandLog | 第一版 30 回合命令量可全量保存。 |
| 地图 | 20x20 以内直接保存完整地块。 |
| 缩略图 | 第一版不默认保存，避免 base64 增大体积。 |
| 配置表 | 不进普通存档，只保存 `rulesVersion`；Debug Export 可附配置摘要。 |

## 十三、Debug Export

Debug Export 是开发阶段定位 bug 的核心工具。它可以从调试面板导出一个 JSON 文件，用来复现“某一局为什么坏了”。

```ts
type DebugExport = {
  exportVersion: number;
  exportedAt: number;
  app: {
    buildVersion: string;
    rulesVersion: string;
    userAgent?: string;
  };
  save?: SaveGame;
  currentState: GameState;
  commandLog: CommandRecord[];
  eventLog: GameEvent[];
  performance: PerformanceSnapshot;
  workerDiagnostics: WorkerDiagnostics[];
  assetDiagnostics: AssetDiagnostics;
};
```

| 内容 | 作用 |
| --- | --- |
| `currentState` | 复现当前局面。 |
| `commandLog` | 检查玩家和 AI 操作链路。 |
| `eventLog` | 看每回合资源、科技、战斗、存档发生了什么。 |
| `performance` | 观察帧率、存档耗时、AI 耗时。 |
| `workerDiagnostics` | 排查 AI/寻路超时和错误。 |
| `assetDiagnostics` | 排查资源版本或缺失图集。 |

| 导出按钮 | 内容范围 |
| --- | --- |
| 导出当前状态 | `GameState` + 最近日志。 |
| 导出完整调试包 | `SaveGame` + `CommandLog` + `EventLog` + 性能摘要。 |
| 导出 Replay 包 | `ReplayPackage` + 期望状态 hash。 |

## 十四、数据一致性校验

读档、存档前、Replay 后都应运行轻量校验。

| 校验 | 规则 | 严重性 |
| --- | --- | --- |
| 玩家引用 | 城市和单位的 `ownerId` 必须存在。 | error |
| 地块引用 | 城市和单位的 `tileId` 必须存在。 | error |
| 双向引用 | `unit.tileId` 对应地块 `unitIds` 应包含单位 ID。 | error |
| 城市上限 | 每方城市数不超过 3。 | warning/error |
| 单位上限 | 每方单位数不超过 10。 | warning/error |
| 当前科技 | `currentTechId` 必须存在且未完成。 | warning |
| 当前阶段 | `phase` 必须是合法枚举。 | error |
| RNG | `rngState` 必须存在。 | error |
| 胜利状态 | 如果 `victory.status = "finished"`，必须有 `winnerId` 和 `type`。 | error |
| 地图尺寸 | `width * height` 必须等于地块数量。 | error |

第一版不建议自动修复规则状态。自动修复可能掩盖 Simulation bug。推荐做法是：阻止读档或保存，提示错误，并允许导出 Debug Export。

## 十五、风险清单

| 风险 | 表现 | 影响 | 预防方案 |
| --- | --- | --- | --- |
| GameState 混入 PixiJS 对象 | 存档失败、读档后对象失效。 | 高 | 类型层限制 `GameState` 只包含纯数据；存档前做 structured clone 测试。 |
| UI 直接改状态 | CommandLog 缺失，回放无法复现。 | 高 | 所有按钮和地图操作都 dispatch Command。 |
| 存档缺版本号 | 字段变化后旧存档直接坏。 | 高 | `SaveGame` 和 `GameState` 都必须有 `schemaVersion`。 |
| 读档时旧 Worker 响应写回 | AI 或寻路结果污染新局。 | 高 | 读档前取消请求，响应必须校验 `gameId`、`turn`、`requestId`。 |
| 随机数不可控 | replay 同步失败。 | 高 | 禁止规则层使用 `Math.random()`，所有随机来自 `rngState`。 |
| EventLog 过大 | 存档越来越慢。 | 中 | 普通存档裁剪日志，全量只 Debug Export。 |
| 配置表变动导致旧局异常 | 科技或单位 ID 找不到。 | 中 | `rulesVersion` + 配置 ID 迁移映射。 |
| IndexedDB 配额不足 | 自动存档失败。 | 中 | 存档失败事件、手动导出 JSON、限制槽位和缩略图。 |
| 浏览器隐私模式限制存储 | 无法保存或持久性弱。 | 中 | 启动时检测存储可用性，失败时提示。 |
| 手动存档覆盖误操作 | 玩家丢失进度。 | 中 | 覆盖确认，第二版做多个槽位。 |
| Replay 只保存快照不保存初始状态 | 难以从头复现。 | 中 | Debug Export 带 `initialState` 或开局快照。 |
| 自动迁移误修坏档 | 旧存档被不可逆改坏。 | 中 | 迁移前保留原始备份或 Debug Export。 |

## 十七、推荐实现顺序

| 顺序 | 工作 | 目的 |
| --- | --- | --- |

| 2 | 实现 `createInitialGameState(seed, settings)`。 | 让新局可重复生成。 |
| 3 | 实现 `validateGameState`。 | 提前发现引用和结构错误。 |
| 4 | 实现 `CommandRecord` 和 `EventLog` 裁剪。 | 支撑调试和回放。 |
| 5 | 实现 `SaveGame` envelope 和预览生成。 | 存档列表可用。 |
| 6 | 接入 IndexedDB `saves/settings` store。 | 完成保存和读取。 |
| 7 | 接入自动存档和手动存档 UI。 | 验证真实流程。 |
| 8 | 实现 `migrateSaveGame` 框架。 | 为后续版本变化预留。 |
| 9 | 实现 Debug Export。 | 支撑 bug 复现和调试。 |
| 10 | 加 Replay 摘要测试。 | 验证确定性。 |

## 十八、结论

第一版数据和存档方案推荐采用：

> **完整 `GameState` 快照 + IndexedDB 存档 + `schemaVersion` 迁移框架 + `CommandLog` 调试回放 + Debug Export。**

这条路线足够稳，也不会提前背上完整录像系统、云存档或多人同步的复杂度。最关键的约束是：**规则数据必须保持纯净，所有状态变化必须经过 Command，存档只保存可迁移的逻辑数据。**
