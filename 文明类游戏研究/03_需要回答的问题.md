# 03 需要回答的问题与推荐决策

这份文件不再只列开放问题，而是把当前阶段的默认答案一起写清楚。后续如果方向变化，再专门改“推荐决策”列。

## A. 游戏定位

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 我们想做多重度？ | 先做中轻度 Web 原型。 | 不直接追完整《文明》体量，先验证 30 回合是否好玩。 |
| 一局理想时长是多少？ | 第一版 20-40 分钟，约 30 回合。 | 控制反馈周期，方便试玩和调参。 |
| 平台是什么？ | 桌面浏览器 Web Demo 优先。 | 移动端第二阶段适配。 |
| 玩家是谁？ | 喜欢策略，但不想读厚手册的玩家。 | UI 和教程要承担解释责任。 |
| 游戏主题是什么？ | 原型先用中性占位主题，后续再定真实历史、架空文明或东方王朝。 | 先别让题材选择阻塞系统验证。 |

## B. 核心循环

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 玩家每回合最主要做哪三件事？ | 探索/建设、选择研究、处理竞争。 | 三件事对应地图、发展、对手压力。 |
| 早期 10 回合如何让玩家立刻有选择？ | 开局给侦察、首都生产、第一科技、附近资源和可选建城点。 | 第一回合就要有可理解选择。 |
| 中期如何制造竞争和路线分化？ | 通过资源分布、邻居压力、科技分支制造差异。 | 不同地图要自然导向不同策略。 |
| 后期如何避免重复操作和拖沓？ | 用胜利赛跑、事件压力、管理自动化减少维护感。 | 第一版先靠 30 回合局长控制规模。 |
| 玩家落后时有没有翻盘路径？ | 预留联盟、危机、奇观、科技追赶、外交制衡。 | 第一版可先用科技追赶和防御建筑。 |

## C. Web 平台与技术路线

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 第一版是桌面 Web 还是移动 Web？ | 桌面 Web 优先。 | 文明类 UI 密度高，移动端会过早限制设计。 |
| 是否需要离线可玩？ | 原型先不要求完整离线，但必须本地存档。 | 后续可升级 PWA 或缓存策略。 |
| 地图用 Canvas 2D、WebGL 还是 WebGPU？ | 第一版用 WebGL2，WebGPU 预留。 | WebGL 稳，适合地图缩放、批量渲染和战争迷雾。 |
| UI 是画在 WebGL 里还是 DOM 里？ | 地图 WebGL，复杂 UI 用 DOM/React。 | 科技树、城市面板、Tooltip 用 DOM 更好维护。 |
| 是否使用渲染库？ | 推荐 PixiJS/WebGL。 | Phaser 作为备选，真 3D 再考虑 Three.js/Babylon.js。 |
| 技术栈是什么？ | TypeScript + Vite + PixiJS/WebGL + React DOM UI。 | 兼顾开发速度、类型安全和 UI 维护。 |

## D. 地图与扩张

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 地图尺寸多大？ | 12x12 到 20x20。 | 足够验证探索和冲突。 |
| 地图是方格、六边形，还是伪 3D？ | 第一版确定使用方格；六边形作为第二版迁移目标。 | 方格更省实现成本；坐标接口仍保留六边形迁移空间。 |
| 是否随机生成？ | 随机资源和地形，但保留固定调试地图。 | 固定地图用于复现 bug 和比较数值。 |
| 城市选址为什么重要？ | 河流、资源、丘陵、海岸影响产出和防御。 | 让地图成为策略，不只是背景。 |
| 扩张的代价是什么？ | 维护费、满意度、距离成本或政策限制。 | 防止无限铺城成为唯一策略。 |

## E. 经济与资源

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 基础资源有哪些？ | 粮食、生产力、金币、科技。 | 第一版保留四种即可。 |
| 哪些资源是局部，哪些是全局？ | 粮食/生产力偏城市局部，金币/科技偏全局。 | 便于城市差异和全局规划同时成立。 |
| 贸易是否重要？ | 第一版只做被动经济加成，不做主动贸易路线或外交交易。 | 主动贸易路线需要新增 Command、UI、AI 和测试，放第二版。 |
| 资源短缺会造成什么问题？ | 战略资源限制高级单位生产。 | 原型可先把战略资源作为第二版。 |
| 是否需要供应线、运输或市场价格？ | 第一版不做。 | 这些系统后续再加，否则范围太大。 |
| 每回合如何计算资源和增长？ | 固定回合结算顺序，并输出结算日志。 | 便于调试和玩家理解。 |

## F. 科技与文化

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 科技树有多少层？ | 原型先做 8-12 个科技。 | 足够产生路线，但不至于失控。 |
| 科技是否绑定时代？ | 第一版不做完整时代，只做早中期科技。 | 时代系统第二版再加。 |
| 玩家能否跳科技？ | 允许少量分支，但保留关键前置。 | 保证自由度和可控性。 |
| 文化/制度是否与科技分开？ | 原型先不分，第二版再加制度。 | 降低第一版复杂度。 |
| 科技领先会不会造成不可逆滚雪球？ | 用成本曲线、防御建筑或追赶机制缓解。 | 第一版重点观察是否过早锁死胜负。 |

## G. 文明差异

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 文明差异来自哪里？ | 第一版只做 2-3 个简单特性。 | 比如生产加成、科研加成、防御加成。 |
| 是否允许领袖和文明分离？ | 记录为可选设计，不进第一版。 | 组合空间大，但平衡成本高。 |
| 每个文明是否有明确玩法主题？ | 需要，但第一版只验证少量风格。 | 不做几十个文明。 |
| 文明强度如何平衡？ | 先用调试数据和短局试玩修正。 | 不追求第一版完全平衡。 |

## H. 外交与战争

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 外交系统是轻量交易，还是核心玩法？ | 第一版只做关系值、紧张状态、宣战和原因解释，不做外交交易。 | 完整外交、交易、停战、结盟后置。 |
| AI 会记仇吗？ | 至少记录宣战、抢地、边境压力等行为。 | 让外交反馈可解释。 |
| 宣战有什么代价？ | 金币成本、关系惩罚或厌战。 | 防止战争成为默认最优解。 |
| 战争胜利是否直接转化为最终胜利？ | 征服可以获胜，但科技胜利也必须可行。 | 至少保留一个非军事胜利。 |
| 是否允许非军事路线有效对抗军事路线？ | 允许，通过防御建筑、战争代价、科技竞速和胜利压力反制。 | 联盟、经济制裁放第二版。 |

## I. 胜利条件

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 有几种胜利条件？ | 第一版做征服胜利 + 科技胜利。 | 一个军事路线，一个非军事路线。 |
| 每种胜利对应的核心行为是什么？ | 征服占首都；科技完成终极项目。 | 胜利条件要对应清晰行为。 |
| 玩家能否看见其他人的胜利进度？ | 必须公开或半公开。 | 形成持续压力。 |
| 是否允许多个玩家同时接近胜利？ | 允许。 | 让终局有紧张感。 |
| 到回合上限时如何结算？ | 30 回合按分数复盘。 | 原型阶段方便快速评估。 |

## J. 输入、存档、部署与调试

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 输入如何适配？ | 鼠标点击、拖拽、滚轮缩放、快捷键结束回合。 | Pointer Events 作为统一输入模型参考。 |
| 是否支持快捷键？ | 至少支持结束回合、打开科技、选中下一个单位。 | 降低重复操作疲劳。 |
| 存档保存哪些内容？ | 地图种子、回合数、玩家状态、AI 状态、城市、单位、科技、外交。 | 以 GameState 为核心保存。 |
| 使用什么存档技术？ | IndexedDB 保存复杂存档，LocalStorage 只保存设置。 | 适合 Web 结构化数据。 |
| AI 和寻路是否会阻塞页面？ | AI、寻路、地图生成预留 Web Worker。 | 防止主线程卡顿。 |
| 是否需要开发者调试面板？ | 第一版必须有。 | 显示 FPS、当前回合、选中单位、AI 状态、资源结算。 |
| 是否需要一键发链接试玩？ | 静态站点部署即可。 | Web 原型的核心优势是快速试玩。 |

## K. 成功标准

| 问题 | 推荐决策 | 备注 |
| --- | --- | --- |
| 试玩 30 回合后，玩家是否想再开一局？ | 这是第一优先级指标。 | 比内容数量更重要。 |
| 玩家是否能说出自己输在哪里？ | 必须能。 | 需要结算复盘和回合日志。 |
| 玩家是否能感到不同地图会产生不同策略？ | 必须能。 | 资源、地形、邻居位置要影响选择。 |
| 玩家是否能在至少两条路线之间纠结？ | 必须能。 | 科技、扩张、军事之间要有资源冲突。 |
| 每回合是否至少有一个有意义的决定？ | 必须观察。 | 这是文明类原型最核心的体验指标。 |
