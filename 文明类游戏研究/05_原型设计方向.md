# 05 Web 原型设计方向

## 最小可玩目标

第一版原型不要追求完整文明体验，只验证两个问题：

| 方向 | 验证问题 |
| --- | --- |
| 玩法 | 玩家在一个小地图上，是否愿意连续做 30 回合的策略选择？ |
| 技术 | WebGL 地图、DOM 面板、回合结算、AI、存档和调试面板能否稳定跑通？ |

## 推荐 Web 原型范围

| 内容 | 推荐范围 | 原因 |
| --- | --- | --- |
| 平台 | 桌面浏览器优先 | 文明类 UI 密度高，先不要被移动端限制。 |
| 技术栈 | TypeScript + Vite + PixiJS/WebGL + React DOM UI | 便于快速开发和后期维护。 |
| 渲染方案 | WebGL2 优先，Canvas 2D 可作为极简 fallback | 地图缩放、战争迷雾、单位批量渲染更适合 WebGL。 |
| UI 方案 | 城市面板、科技树、外交面板、回合提示用 DOM/React | 表格、按钮、Tooltip 用 DOM 更快更清楚。 |
| WebGPU | 不进第一版核心，渲染层预留接口 | 第一版先稳定验证玩法和 WebGL。 |
| 地图 | 方格或六边形，12x12 到 20x20，支持缩放和平移 | 足够产生探索和冲突，也能验证 WebGL 地图操作。 |
| 玩家 | 1 名玩家 + 1 个简单 AI | 降低 AI 和外交复杂度。 |
| 城市 | 每方最多 3 座城市 | 控制管理压力。 |
| 资源 | 粮食、生产力、金币、科技 | 覆盖成长、建造、经济和研究。 |
| 地形 | 平原、森林、丘陵、河流、山脉、水域 | 足够让选址和移动产生差异。 |
| 单位 | 侦察兵、战士、建造者、弓手 | 覆盖探索、近战、建设、远程。 |
| 科技 | 8 到 12 个科技 | 足够形成路线，但不会失控。 |
| 建筑 | 粮仓、工坊、市场、学院、城墙 | 对应人口、生产、经济、科技、防御。 |
| 胜利 | 征服胜利 + 科技胜利 | 一个军事路线，一个非军事路线。 |
| 存档 | IndexedDB 至少保存一局 | 方便测试和玩家中断后继续。 |
| 输入 | 鼠标点击、拖拽、滚轮缩放、快捷键结束回合 | Web 桌面版基础操作。 |
| 调试面板 | FPS、当前回合、选中单位、AI 状态、资源结算 | 方便开发阶段定位问题。 |
| 部署 | 静态站点部署，发链接即可试玩 | Web 原型的优势是快速收集反馈。 |

## 30 回合体验草案

| 阶段 | 回合 | 玩家体验 | 技术验证 |
| --- | --- | --- | --- |
| 开局探索 | 第 1-5 回合 | 玩家拥有首都、侦察兵、战士；探索战争迷雾；发现资源、遗迹或建城点。 | WebGL 地图、战争迷雾、选中高亮、拖拽缩放、单位移动。 |
| 第一次扩张 | 第 6-12 回合 | 玩家生产建造者或移民，研究第一个科技，选择经济、军事或探索路线。 | DOM 城市面板、科技选择、生产队列、资源结算日志。 |
| 路线分化 | 第 13-22 回合 | 玩家建立第二城，资源开始不均衡，AI 或中立势力形成压力。 | AI Worker、寻路、固定回合结算、胜利进度面板。 |
| 第一次战略冲突 | 第 23-30 回合 | AI 接近边境，关键资源点产生争夺，玩家看到征服或科技胜利距离。 | 战斗结算、路径预览、存档读档、复盘面板。 |

## 第一版必须做

| 模块 | 内容 |
| --- | --- |
| WebGL 地图 | Tilemap、单位 Sprite、资源图标、缩放、平移、选中高亮。 |
| DOM UI | 城市面板、科技面板、回合按钮、Tooltip、胜利进度、调试面板。 |
| GameState | 地图、城市、单位、科技、AI、回合数、胜利进度统一管理。 |
| 回合系统 | 玩家输入、AI 决策、城市生产、资源结算、胜利检测按固定顺序执行。 |
| 存档 | IndexedDB 保存/读取当前局。 |
| 调试 | 固定地图种子、FPS、资源日志、AI 意图、选中对象信息。 |
| 新手引导 | 前 5 分钟引导移动、生产、研究、结束回合。 |

## 第一版不要做

| 不做内容 | 原因 |
| --- | --- |
| 完整外交 | AI 和 UI 工作量太大，先做轻量关系值和宣战。 |
| 几十个文明 | 平衡成本高，第一版只做 2-3 个简单特性。 |
| 大科技树 | 会拖慢验证，先做 8-12 个科技。 |
| 复杂宗教 | 系统独立度高，容易扩大范围。 |
| 海战 | 地图、寻路、单位规则都要额外扩展。 |
| 完整时代系统 | 第二版再做时代变化和时代事件。 |
| 多人 | 网络同步和回合一致性会显著增加复杂度。 |
| 第一版直接 WebGPU | 技术风险和兼容验证成本较高。 |
| 纯 WebGL UI | 科技树、城市面板、Tooltip 用 DOM 更合适。 |

## 需要观察的试玩指标

| 指标 | 观察方法 |
| --- | --- |
| 玩家是否理解每回合该做什么 | 看是否频繁停住、乱点或找不到结束回合。 |
| 玩家是否会因为地图不同而改变策略 | 比较不同种子下的建城点、科技和扩张路线。 |
| 玩家是否觉得城市选址重要 | 观察是否会比较资源、河流、防御和距离。 |
| 玩家是否能看懂科技收益 | 观察是否能说出为什么选某个科技。 |
| 玩家是否比较现在收益和未来收益 | 观察生产、研究、扩张、军事之间是否有纠结。 |
| 玩家是否想重开一局试不同路线 | 试玩结束后直接询问。 |
| 平均每回合操作次数 | 通过事件日志记录。 |
| 第几回合遇敌 | 通过回合日志记录。 |
| 拖拽缩放是否卡顿 | 通过 FPS 面板和主观反馈判断。 |
| AI 思考是否卡住页面 | 通过主线程卡顿和 Worker 执行时间观察。 |

## 可选创新方向

| 方向 | 说明 |
| --- | --- |
| 三时代压缩 | 把文明发展压缩成三个时代，每个时代结束时发生一次世界变化。 |
| 地区影响力 | 用地区影响力替代纯粹铺城，减少后期城市管理压力。 |
| 科技随机分支 | 科技树引入少量随机分支，让每局研究路线不完全相同。 |
| 轻外交 | 第一版只做关系值、紧张状态、宣战和原因解释；交易系统后续再扩展。 |
| 公开胜利赛跑 | 把胜利条件设计成公开赛跑，让玩家持续感到压力。 |
