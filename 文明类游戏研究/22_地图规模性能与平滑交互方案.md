# 22 地图规模性能与平滑交互方案

## 一、核心结论

地图不能只为了不卡而做小。文明类/4X 游戏需要“世界感”：探索未知、发现资源、选择扩张方向、和 AI 争夺空间。如果地图太小，性能会轻松，但玩法会像棋盘小关卡，缺少文明发展感。

第一版推荐：

| 阶段 | 地图规模 | 目的 |
| --- | --- | --- |
| 技术 Spike | 20x20 | 验证 WebGL 渲染、拖拽、缩放、命中、迷雾、性能采样。 |
| 第一版默认体验 | 16x16 | 保持世界感和开发复杂度平衡。 |
| 第一版支持范围 | 12x12 到 20x20 | 12x12 用于快速调试，20x20 用于压力测试。 |
| 第二版目标 | 32x32 到 64x64 | 需要 chunk、culling、批处理、Worker 寻路/AI。 |
| 长期大地图 | 64x64+ | 需要更系统的地图分页、AI 分区、视野增量、GPU/mesh 优化。 |

这些规模不是性能事实。它们是开发阶段目标，必须由本地原型实测确认。

## 二、地图太小的问题

| 问题 | 表现 | 影响 |
| --- | --- | --- |
| 探索感弱 | 开局几回合就看完整张地图。 | 4X 的探索乐趣下降。 |
| 扩张选择少 | 第二城位置非常有限。 | 城市选址不再是战略承诺。 |
| AI 压力太早 | 玩家和 AI 很快贴脸。 | 变成小型战棋，而不是文明发展。 |
| 胜利路线短 | 科技、经济、军事还没分化就结束。 | 多路线竞争不明显。 |
| 重开价值低 | 地图随机差异不够产生不同策略。 | 玩几局后容易重复。 |

因此第一版不建议低于 12x12。更合适的是默认 16x16，压力测试 20x20。

## 三、地图扩大后的性能风险

地图扩大不只影响渲染。

| 系统 | 地图变大后的风险 | 应对方向 |
| --- | --- | --- |
| 渲染 | tile、资源、单位、迷雾对象变多。 | atlas、layer 分层、culling、chunk。 |
| 平移/缩放 | 每帧需要更新更多对象和命中区域。 | 只移动 root container，不逐个移动 tile。 |
| 点击命中 | 坐标换算复杂度增加，尤其六边形/多层对象。 | CPU 坐标换算优先，复杂后 GPU picking。 |
| 战争迷雾 | 每回合视野刷新可能扫描更多地块。 | dirty tile、视野增量、分区更新。 |
| 寻路 | AI 和路径预览的搜索空间变大。 | A* 限制范围、缓存、Worker。 |
| AI | 建城点评分、威胁评估、目标选择变重。 | AIReadableState 裁剪、候选数量限制、Worker。 |
| 存档 | 地块数量和日志变多。 | schemaVersion、压缩摘要、只保存必要状态。 |
| 调试 Overlay | 坐标/路径/AI 目标显示会拖慢。 | Debug overlay 默认关闭，按层开关。 |

## 四、规模分级策略

| 地图规模 | tile 数 | 第一版处理 | 备注 |
| --- | ---: | --- | --- |
| 12x12 | 144 | 调试图 | 快速测试规则、教学、UI。 |
| 16x16 | 256 | 默认体验图 | 第一版平衡点。 |
| 20x20 | 400 | 压力测试图 | 必须测拖拽、缩放、迷雾、AI、存档。 |
| 32x32 | 1024 | 第二版候选 | 需要 chunk/culling，不建议第一版默认。 |
| 64x64 | 4096 | 长期目标 | 必须重做 AI、寻路、视野、渲染策略。 |
| 128x128 | 16384 | 不建议 Web 第一版考虑 | 需要严肃的大地图架构。 |

## 五、平移怎么做到平滑

关键原则：**相机移动时只改变地图根容器的 transform，不逐个改 tile 坐标。**

| 做法 | 说明 |
| --- | --- |
| `rootWorldContainer.position` | 平移整个世界容器。 |
| `rootWorldContainer.scale` | 缩放整个世界容器。 |
| tile 坐标固定 | tile 的 world 坐标初始化后不随相机变化。 |
| 输入只改 CameraState | Pointer drag 改相机状态，RenderEngine 根据 CameraState 更新容器。 |
| 使用 `requestAnimationFrame` | 输入事件只记录目标状态，真正渲染更新在 animation frame 中执行。 |
| 惯性/平滑插值 | 可选，用当前 camera 向目标 camera lerp，避免跳变。 |
| 限制缩放范围 | 避免过小看不清或过大造成纹理浪费。 |

示意：

```ts
type CameraState = {
  x: number;
  y: number;
  zoom: number;
  targetX: number;
  targetY: number;
  targetZoom: number;
};

function updateCamera(camera: CameraState, dt: number) {
  const t = 1 - Math.exp(-dt * 18);
  camera.x += (camera.targetX - camera.x) * t;
  camera.y += (camera.targetY - camera.y) * t;
  camera.zoom += (camera.targetZoom - camera.zoom) * t;
  rootWorldContainer.position.set(camera.x, camera.y);
  rootWorldContainer.scale.set(camera.zoom);
}
```

## 六、缩放怎么做到平滑

| 技术点 | 做法 |
| --- | --- |
| 以鼠标位置为缩放中心 | 缩放前后保持鼠标下的 world point 不变。 |
| 缩放节流 | wheel 事件可能很密，累积 targetZoom，在 rAF 中更新。 |
| 缩放插值 | 当前 zoom 追 targetZoom，而不是立即跳到目标。 |
| 资源图标 LOD | 缩太小时隐藏小图标/文字，只保留地形和城市。 |
| Debug 文本关闭 | 缩放/拖拽时不要显示大量 BitmapText。 |
| DPR 封顶 | 高分屏下限制 renderer resolution，避免 canvas 过大。 |

以鼠标为中心缩放的核心：

```ts
function zoomAt(screenPoint: ScreenPoint, nextZoom: number) {
  const before = screenToWorld(screenPoint, camera);
  camera.targetZoom = clamp(nextZoom, minZoom, maxZoom);
  const after = screenToWorld(screenPoint, {
    ...camera,
    zoom: camera.targetZoom,
  });
  camera.targetX += (after.x - before.x) * camera.targetZoom;
  camera.targetY += (after.y - before.y) * camera.targetZoom;
}
```

## 七、渲染优化分层

| 优化 | 第一版 | 第二版 | 说明 |
| --- | --- | --- | --- |
| Texture Atlas | 必做 | 继续 | PixiJS 官方建议尽量使用 spritesheet 减少纹理数量。 |
| Sprite tilemap | 必做 | 可升级 mesh/chunk | 第一版地图小，先用 Sprite + atlas。 |
| Culling | 轻量 | 系统化 | PixiJS 文档提醒 culling 可应用层做，但要看 CPU/GPU 瓶颈。 |
| Chunk | 接口预留 | 必做 | 32x32+ 后按 8x8/16x16 chunk 管理。 |
| Dirty update | 建议 | 必做 | 迷雾、领土、道路只更新变化区域。 |
| LOD | 建议 | 必做 | 缩小时隐藏资源数字、单位血条、debug 文本。 |
| Debug overlay 开关 | 必做 | 继续 | 调试层不能参与正式性能判断。 |
| WebGPU | 不做 | 评估 | 不是第一版核心。 |

## 八、世界感与性能的折中方案

如果担心地图小，可以不用一开始就做大地图，而是用设计手法增强世界感。

| 方法 | 说明 | 性能影响 |
| --- | --- | --- |
| 战争迷雾 | 让未知区域存在悬念。 | 中，需要视野刷新。 |
| 地形区域差异 | 北部山地、南部河谷、东部森林。 | 低。 |
| 关键资源点 | 让扩张方向有明确诱因。 | 低。 |
| AI 从迷雾外出现 | 不需要超大地图也有外部压力。 | 低到中。 |
| 地图边缘提示 | 远方传闻、遗迹、资源线索。 | 低。 |
| 30 回合短局 | 缩短地图需求，强化每回合选择。 | 低。 |

第一版可以用 16x16 做出“足够的世界感”：玩家开局只看见 4-6 格范围，资源和 AI 不完全暴露，第二城候选点至少 2-3 个。

## 九、必须实测的地图性能 Spike

| Spike | 场景 | 要记录 |
| --- | --- | --- |
| 16x16 默认局 | 地形、资源、迷雾、2 城、5 单位 | FPS、p95 frame time、sprite count |
| 20x20 压力局 | 地形、资源、迷雾、双方 3 城 10 单位 | FPS、p95、draw calls 如可取、内存趋势 |
| 平移测试 | 连续拖拽 10 秒 | frame time、input latency |
| 缩放测试 | 连续滚轮缩放 10 秒 | frame time、LOD 切换耗时 |
| 迷雾刷新 | 单位移动后刷新视野 | fog update duration |
| Debug overlay | 开/关坐标、AI 路径、可见性 | Debug 对性能的影响 |
| 32x32 探索性测试 | 第二版预研 | 判断是否必须 chunk/mesh |

## 十、回答你的问题

| 问题 | 回答 |
| --- | --- |
| 地图做多大才不会卡？ | 现在不能凭空保证。第一版应以 16x16 默认、20x20 压力测试，用原型数据判断。 |
| 做太小是不是不卡？ | 通常会更轻，但玩法世界感会弱，探索、扩张、AI 压力都会受影响。 |
| 地图扩大性能会不会损失很大？ | 会增加渲染、视野、寻路、AI、存档成本；如果只扩大地图但不做 chunk/culling/Worker，会明显变重。 |
| 平移缩放怎么平滑？ | 相机只改 root container 的 position/scale；输入事件改 target camera；rAF 中插值更新；缩小时做 LOD。 |
| 详细端能不能做到？ | 可以做到，但必须分阶段：第一版 16x16/20x20 验证，第二版 32x32 做 chunk/culling，长期 64x64+ 再做更大架构。 |

## 十二、结论

地图大小不是单纯性能问题，而是玩法体验问题。

- 12x12 适合调试。
- 16x16 适合第一版默认。
- 20x20 适合第一版压力测试。
- 32x32 是第二版扩展目标。
- 64x64+ 需要大地图架构，不应在第一版承诺。

平滑平移缩放是可以做到的，关键是相机容器 transform、rAF、插值、LOD、atlas、culling 和性能采样一起做。真正能不能达到预算，必须用本地原型实测。
